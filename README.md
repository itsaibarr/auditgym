# AuditGym: RL-среда для обучения и оценки ИИ-аудиторов

Команда tryHard, Genesis Hackathon, трек FinTech.

AuditGym генерирует бухгалтерию вымышленной компании за один месяц, вносит в неё ошибки и проверяет, найдёт ли их агент. Генератор сначала строит правильные книги, потом вносит ошибку, записывает, что именно изменилось, и уже из этой записи выводит эталон. Агент видит записи только через несколько инструментов и в конце отправляет выводы с доказательствами. Оценщик работает вне процесса агента, сопоставляет выводы с эталоном и считает награду кейса.

Мы сделали среду и оценщик. Агента, чат-бота и аудиторского заключения в этом репозитории нет.

## Для жюри: одна команда

Ставить ничего не нужно. Python, git, ключи, аккаунты и GPU не понадобятся. Выберите строку по тому, что есть на компьютере. Команда сразу печатает первую строку, скачивает маленький лаунчер и печатает план; при первом запуске 20–60 секунд готовит Python и пакеты, затем около минуты идёт тур:

| Что есть на компьютере | Команда |
|---|---|
| macOS / Linux (только `curl`) | `echo "[auditgym] fetching the launcher (7 KB) ..."; curl -fsSL https://raw.githubusercontent.com/itsaibarr/auditgym/master/run.sh \| sh` |
| Node.js 16+ (`npx`) | `npx -y --no-update-notifier https://codeload.github.com/itsaibarr/auditgym/tar.gz/master` |
| Linux только с `wget` (например, Ubuntu Desktop) | `echo "[auditgym] fetching the launcher (7 KB) ..."; wget -qO- https://raw.githubusercontent.com/itsaibarr/auditgym/master/run.sh \| sh` |
| Docker (в т.ч. Windows) | `docker build -t auditgym:1.0.0 https://github.com/itsaibarr/auditgym.git`, затем `mkdir -p auditgym-report && docker run --rm --network none --user "$(id -u):$(id -g)" -v "$PWD/auditgym-report:/report" auditgym:1.0.0 tour --out /report` <br>Windows PowerShell: `mkdir -Force auditgym-report; docker run --rm --network none -v "${PWD}/auditgym-report:/report" auditgym:1.0.0 tour --out /report` |

Тур показывает всё сразу на новых сидах. Если вы проверяете по процессу кейса, со своими политиками и своими скрытыми сидами, переходите к разделу «Проверка организаторов по разделу 06 кейса».

### Первый запуск

Лаунчер скачивает `uv` версии 0.12.17 в `~/.cache/auditgym` и сверяет его SHA-256. Дальше `uv` ставит Python 3.11 и зависимости, закреплённые в `uv.lock`. Кроме этой папки пишутся только кеши самого uv, `~/.cache/uv` и `~/.local/share/uv`. Системный Python, PATH и профиль оболочки остаются как были.

Первые несколько секунд npx сам скачивает пакет и показывает только свой значок загрузки, затем лаунчер пишет, что он делает. На обычной сети разовая настройка занимает 20–60 секунд, на медленной до 3 минут, потом около минуты (40–90 секунд) идёт тур. Пока идёт настройка, лаунчер каждые 2 секунды пишет строку: что сейчас ставится, сколько секунд прошло и сколько мегабайт уже на диске. Каждая загрузка делает до трёх попыток. Если сеть так и не ответила, лаунчер выходит с кодом 2 и не оставляет недокачанных файлов, так что достаточно повторить ту же команду.

Потом команды стартуют за несколько секунд и работают без сети:
- `npx -y --no-update-notifier --offline https://codeload.github.com/itsaibarr/auditgym/tar.gz/master <команда>`;
- `sh ~/.cache/auditgym/src-master/run.sh <команда>`, если ставили через curl или wget;
- собранный образ Docker.

Эти строки мы запускали на публичных URL в чистых контейнерах `node:16`, `node:22-slim`, `node:24`, `node:22-alpine`, в Debian с curl, в Ubuntu только с wget, в Fedora и Alpine, на macOS с пустым HOME, в Docker с `--user` и из папки с пробелом в имени. На Windows npx собирает образ и запускает тур в Docker. Эту ветку мы проверяли в эмуляции, а шаги PowerShell запускали в pwsh 7. На настоящем Windows её никто не запускал.

### Что показывает тур

Без аргументов запускается `auditgym tour`. Он идёт около минуты (40–90 секунд), проходит четыре шага и печатает итог по критериям кейса. Весь вывод CLI на английском. Над каждым шагом тур пишет, что он проверяет и сколько это обычно длится. Пока шаг идёт, его стадии видны списком, как в Docker BuildKit: у текущей крутится индикатор, растёт счётчик (например, 463/575 тестов или 70/100 эпизодов) и идёт время, а законченная стадия получает ✓ и своё время. Во время pytest строка ещё называет, что проверяется прямо сейчас.

1. **Закрытая проверка в форме организаторов.** Тур берёт новые секретные сиды и соль и генерирует 20 эпизодов, из них 5 чистых и 5 со связанными ошибками. Данные каждого эпизода проверяет код, который не импортирует генератор. Он проверяет три вещи: инварианты I1–I8 на книгах до ошибок, совпадение нарушений с объявленными ошибками и то, что доказательства воспроизводят суммы. Затем на этих эпизодах работают random, reconcile, flag_all, oracle и наш expert. Таблица показывает P, R, F1, награду, награду на чистых книгах, шаги и время на эпизод. Порядок наград тур проверяет так: oracle получает 1.0 везде, flag_all получает −1 на чистых книгах, а на книгах с ошибками expert > reconcile ≥ max(flag_all, random). Строка с порядком печатает измеренные средние. Если в split нет ни одной книги с ошибками, тур так и пишет: «order on books with errors not checked».
2. **20 парных проверок.** В закрытых эпизодах тур переставляет строки и меняет ID документов и строк. Oracle должен остаться на 1.0, исход expert меняться не должен.
3. **Повтор, целостность, утечки.** Тур побайтно повторяет закрытый прогон и заново его оценивает, сверяет папки прогонов с хешами и подписью HMAC в `run.json` и прогоняет leakscan по наблюдениям.
4. **Официальная проверка.** Самый долгий шаг, поэтому он последний: результаты видны раньше. Тур запускает `auditgym check`, это 153 проверки: pytest, базовые политики, порядки наград, leakscan, парные проверки и replay. Результат сгруппирован по критериям кейса.

Итог по пяти критериям кейса берёт статус каждой строки только из измерений этого запуска, а в колонке «Evidence from this run» стоят сами числа. Пятый критерий, инженерию и объяснение, тур не измеряет. В этой строке стоит «not measured» и ссылки, где смотреть.

Под итогом тур печатает «Next steps»: до четырёх готовых команд, каждая подписана задачей, которую она решает. Полный список лежит в `report.md`, а `auditgym --help` объясняет каждую команду и когда её запускать. Последняя строка на экране показывает вердикт: «✓ ALL PASSED · 4 of 4 measured criteria passed», время и путь к отчёту. В них уже подставлена ваша команда запуска. Если тур запущен через npx на Windows, команды напечатаны в синтаксисе PowerShell. После строки с псевдонимом первая команда повторяет и перепроверяет закрытый прогон этого тура.

Отчёт лежит в `auditgym-report/`:
- `report.md` и `report.json`: итог по критериям со статусами, таблица политик, результаты шагов;
- `check/summary.md`: каждая проверка `check` отдельной строкой;
- `closed/`: папки прогонов пяти политик, а также `split.json` и одноразовая соль `SALT` этого тура, по ним `replay` перепроверяет прогон.

Свои сиды и свою соль тур на диск не пишет.

### Что дальше: сценарии жюри

Ниже `auditgym` означает вашу команду запуска: `npx -y --no-update-notifier https://codeload.github.com/itsaibarr/auditgym/tar.gz/master`, `sh ~/.cache/auditgym/src-master/run.sh` или `docker run --rm -i --network none -v "$PWD/out:/out" auditgym:1.0.0`. Тур печатает их уже подставленными. В Docker сначала `mkdir -p out`, добавьте `--user "$(id -u):$(id -g)"` на Linux и пишите результаты в `/out/...` вместо `out/...`.

| Задача | Команда |
|---|---|
| Свой закрытый split: новые случайные сиды в форме организаторов, 5 чистых, 5 связанных и 10 прочих. Сиды и параметры можно править, ключи перечислены в таблице ниже | `auditgym split > my_split.json` |
| Итог по критериям на **ваших** сидах | `auditgym tour --split - < my_split.json` |
| Наши адаптеры четырёх политик кейса на вашем split: P, R, F1, награда, шаги, время, падения | `auditgym run --policy random,reconcile,flag_all,oracle --split - --public-salt --out out < my_split.json` |
| Сравнить прогоны с разбивкой по типам ошибок | `auditgym compare out/random out/reconcile out/flag_all out/oracle --per-type` |
| Своя политика: класс Python с `reset/step`. `auditgym init my-agent` кладёт копию примера `examples/my_policy.py` в `./my-agent` для правки и печатает команду запуска | `auditgym run --policy my_policy:LookAround --policy-path examples --split dev --out out --trust-policies` |
| Своя политика: любая программа, JSON-строки через stdin/stdout, пример в `examples/stdio_policy.py` | `auditgym run --policy "cmd:python3 /abs/path/stdio_policy.py" --split dev --out out --trust-policies` |
| Сыграть эпизод вручную, получить JSON Schema для LLM | `auditgym play` · `auditgym schema --out out/schema` |

`--policy-path examples` работает из любой папки: если такой папки рядом нет, берётся `examples` из самого пакета.

Если политика не импортируется или программа не найдена, `run` останавливается сразу, с понятной ошибкой и кодом 2. Если политика упала или вышла по тайм-ауту во всех эпизодах, `run` отмечает это в колонке `Crashed or timed out` и выходит с кодом 1. Флаг `--trust-policies` нужен только вне Docker: там установка доступна вам на запись, а оценщик работает в том же процессе. Аргументы политик передаются через `--policy-arg key=value`, например `--policy-arg seed=7` для `random`. Неизвестный ключ для встроенной политики даёт ошибку. Программы на Node.js, Go или JVM создают потоки, поэтому на Linux им нужен `--allow-forks`, который снимает лимит процессов. На macOS он не нужен. В образе Docker есть только Python. Для другого языка соберите свой образ: `FROM auditgym:1.0.0` + `USER root` + `RUN apt-get update && apt-get install -y nodejs` + `USER auditor`.

Если задать `AUDITGYM_SALT` при запуске через npx или run.sh, соль окажется в окружении процессов-обёрток, и политика могла бы её прочитать. Тур тогда берёт случайную соль и печатает жёлтое «Note». `run` с такой солью отказывается стартовать. Строгая проверка с вашей солью идёт в Docker, рецепт в разделе «Закрытая проверка».

Ключи конфигурации. В split они задаются в `base_config` и в `config` у эпизода. Неизвестный ключ даёт ошибку.

| Ключ | По умолчанию | Допустимо |
|---|---|---|
| `errors.<тип>.on`, `errors.<тип>.count` | `true`, `[0, 2]` | типы `duplicate_invoice`, `payment_allocation`, `fx_conversion`, `period_cutoff`; `count` = `[min, max]` |
| `interacting.X1`, `interacting.X2` | `0.0` | вероятность 0–1 связанного сценария |
| `max_errors` | 12 | 0–25 |
| `base_currencies` / `foreign_currencies` | `[KZT, USD, EUR]` / `[USD, EUR, KZT, JPY, KWD, CNY, GBP]` | ISO-коды среды |
| `timezones` | `[Asia/Almaty, Asia/Tashkent, Europe/Berlin, Asia/Dubai, UTC]` | любые IANA-зоны |
| `year`, `months` | 2026, 1–12 | 1971–2200, подмножество 1–12 |
| `cutoff_window_days` | 5 | 4–60 |
| `customers`, `invoices`, `opening_invoices`, `on_account`, `expenses` | `[6,16]`, `[20,70]`, `[2,6]`, `[1,3]`, `[60,260]` | `[min, max]`; `invoices` считает основные продажи периода, к ним добавляются счета начального сальдо, возвраты и кредит-ноты; у `customers` минимум 2 (клиент в базовой и клиент в иностранной валюте); до 200 / 2000 / 200 / 200 / 5000 |

## Проверка организаторов по разделу 06 кейса

Кейс описывает, как жюри проверяет среду: свои четыре политики на своих 20 скрытых эпизодах, 20 парных проверок, независимая проверка данных и эталона, диагностика P, R, F1, возврата, шагов и времени. Ниже этот процесс по шагам, каждый шаг одна команда в контейнере без сети, с лимитами кейса: Python 3.11, 2 CPU, 4 ГБ, 60 секунд на эпизод, 100 шагов. Лимиты эпизода среда соблюдает сама.

```bash
# 1. Образ и единая команда проверки                                      → четыре измеряемых критерия, код 0 = всё пройдено
docker build -t auditgym:1.0.0 https://github.com/itsaibarr/auditgym.git
docker run --rm --network none --cpus 2 --memory 4g auditgym:1.0.0 check

# 2. Свои скрытые эпизоды: шаблон split в форме кейса (5 чистых, 5 со связанными ошибками, 10 прочих).
#    Замените seed на свои; ключи config перечислены ниже в таблице «Ключи конфигурации».
docker run --rm --network none auditgym:1.0.0 split > my_split.json
SALT=$(openssl rand -hex 32)    # секретная соль: без неё эталон можно восстановить открытым генератором

# 3. Четыре политики на этих эпизодах: P, R, F1, возврат, шаги, время, падения   → диагностика из раздела 10
mkdir -p out && docker run -i --rm --network none --cpus 2 --memory 4g --user "$(id -u):$(id -g)" \
    -e AUDITGYM_SALT=$SALT -v "$PWD/out:/out" auditgym:1.0.0 \
    run --policy random,reconcile,flag_all,oracle --policy-arg seed=7 --split - --out /out < my_split.json

# 4. Данные и эталон, независимо по записям                               → «Данные и эталон», 25
docker run -i --rm --network none --cpus 2 --memory 4g -e AUDITGYM_SALT=$SALT auditgym:1.0.0 datacheck --split - < my_split.json

# 5. 20 парных проверок: перестановка строк и смена ID                    → «Воспроизводимость и обобщение», 15
docker run -i --rm --network none --cpus 2 --memory 4g -e AUDITGYM_SALT=$SALT auditgym:1.0.0 paired --split - < my_split.json

# 6. Точный повтор seed и действий, целостность прогонов, утечки          → «Воспроизводимость», «Контракт и изоляция»
docker run -i --rm --network none --cpus 2 --memory 4g -e AUDITGYM_SALT=$SALT -v "$PWD/out:/out:ro" auditgym:1.0.0 \
    replay /out/reconcile --split - < my_split.json
docker run --rm --network none --cpus 2 --memory 4g -v "$PWD/out:/out:ro" auditgym:1.0.0 leakscan /out/random /out/reconcile /out/flag_all /out/oracle
```

Пояснения к шагам:
- **Шаг 3.** `--policy-arg seed=7` задаёт фиксированный seed случайного исследователя. Вместо наших адаптеров можно подключить свои политики: класс Python с `reset/step` или любую программу с JSON-строками через stdin/stdout, см. раздел «Как подключить свою политику». Модуль монтируется как `-v "$PWD/policies:/policies:ro"` с флагом `--policy-path /policies`.
- **Шаг 2.** Формат split: `base_config` общий для всех эпизодов, у каждого эпизода `seed` (целое число или строка) и свой `config`. Ключи `config` эпизода заменяют одноимённые ключи `base_config` целиком, ключ, которого нет ни там, ни там, берёт значение по умолчанию из таблицы «Ключи конфигурации». Поле `profile` служит только подписью. `generate` называет папки `ep_00`, `ep_01` и так далее в порядке split.
- **Шаг 4.** `datacheck` перегенерирует каждый эпизод и проверяет три вещи: равенства I1–I8 на книгах до внесения ошибок, ровно объявленные расхождения после, доказательства воспроизводят суммы. Код проверки не импортирует генератор. Чтобы проверить своим кодом, выгрузите эпизоды вместе с `truth.json` и `provenance.json` командой `generate` из раздела «Закрытая проверка».
- **Шаг 5.** `paired` копирует каждый эпизод с перестановкой строк и новыми ID документов и строк. Oracle на копии должен получить 1.0 под новыми ID, это и есть парная проверка кейса. Результат и код выхода определяет только эта проверка. Для остальных политик `paired` печатает по строке: дают ли они тот же ответ на копии (те же найденные ошибки, ложные тревоги и пропуски). Ответ сравнивается по сути: какие ошибки найдены и какие документы обвинены (тип и ID, ID копии переводятся обратно в ID оригинала), сумма в сравнении не участвует. Если ответ политики зависит от порядка строк, это её свойство, а не провал среды; если отличается только награда из-за другого числа шагов, это тоже просто информация. Свои политики добавляются так: `paired --policy expert,reconcile,my_module:MyAgent --policy-path /policies`.
- **Для скриптов жюри.** У `run` и `compare` есть `--format md|csv|json`: таблица для файла или разбора без рамок. Без терминала таблицы печатаются шириной до 400 колонок и не обрезаются.
- **Контракт** проверяется тестами в шаге 1, а вручную через `AuditEnv` или `gym.make("AuditGym-v1")`, см. раздел «Контракт среды».

## Закрытая проверка

Это строгий вариант для настоящих скрытых сидов. Секретную соль длиной от 32 символов видит только раннер. Split идёт через stdin, поэтому сидов нет ни в argv раннера, ни в смонтированных файлах. Все политики запускаются одним вызовом в новую пустую папку результатов.

```bash
SALT=$(openssl rand -hex 32)   # сохраните: нужна для replay и перегенерации эпизодов; не кладите в смонтированные папки
mkdir -p out eps               # образ работает от пользователя auditor: на Linux передайте свой uid
docker run -i --rm --network none --user "$(id -u):$(id -g)" -e AUDITGYM_SALT=$SALT -v "$PWD/out:/out" \
    auditgym:1.0.0 run --policy random,reconcile,flag_all,oracle,my_policy:LookAround --policy-path /app/examples \
    --split - --out /out < my_split.json
# свои политики: положите модуль в ./policies и добавьте -v "$PWD/policies:/policies:ro" и --policy-path /policies
docker run --rm --network none -e AUDITGYM_SALT=$SALT -v "$PWD/out:/out:ro" auditgym:1.0.0 compare /out/random /out/reconcile /out/flag_all /out/oracle --per-type
# повтор закрытого прогона (включая oracle: его ответ восстанавливается из перегенерированного эталона)
docker run -i --rm --network none -e AUDITGYM_SALT=$SALT -v "$PWD/out:/out:ro" auditgym:1.0.0 replay /out/reconcile --split - < my_split.json
# эпизоды закрытого split на диск — для независимой проверки после прогона (не давайте их политике)
docker run --rm --network none --user "$(id -u):$(id -g)" -e AUDITGYM_SALT=$SALT -v "$PWD/my_split.json:/s.json:ro" -v "$PWD/eps:/eps" \
    auditgym:1.0.0 generate --split /s.json --out /eps
```

Раннер надо запускать напрямую. С `--init`, с обёрткой `sh -c` или `uv run` и с солью в командной строке он не стартует, потому что соль тогда может прочитать другой процесс. Код 2 дают и такие ошибки: закрытый eval без соли или с короткой солью, `--seeds` или `--config` вместо stdin, split-файл по пути, `--episodes` с папкой, где лежит `_grader/`.

## Как подключить свою политику

```bash
# встроенные: random | reconcile | flag_all | expert | oracle (oracle только внутри раннера)
auditgym run --policy random,reconcile,flag_all,oracle --split dev
# своя Python-политика (класс с reset/step), запускается в изолированном дочернем процессе
auditgym run --policy my_policy:LookAround --policy-path examples --split dev --trust-policies
# любая программа на любом языке, протокол JSON-строк через stdin/stdout
auditgym run --policy "cmd:python3 /abs/path/examples/stdio_policy.py" --split dev --trust-policies
# таблица сравнения: P, R, F1, возврат, экспериментальная награда, шаги, доля FP на чистых, время, падения
auditgym compare runs/oracle runs/reconcile runs/flag_all runs/random --per-type
```

Строгий закрытый прогон со своими сидами описан выше, в разделе «Закрытая проверка».

Справка для своей политики:
- первое наблюдение (`reset`) содержит ключи `task`, `manifest`, `policy`, `tables`, `available_actions`, `action_format`, `finding_types`, `limits`, `steps_remaining`; каждое следующее (`step`) содержит `result`, `error`, `steps_remaining`, в `info` всегда лежат `error_code` и `steps_remaining`;
- `get_record` возвращает `{"table", "record"}`, `get_document` возвращает `{"doc_id", "kind", "document"}`; минимальные наборы доказательств для каждого типа ошибки агент видит в первом наблюдении: `policy.findings.minimal_evidence`;
- ответ `list_records` лежит в `result` и содержит `table`, `rows` (до 50 строк), `next_cursor` (null на последней странице) и `total`; ошибка приходит в `error` как `{"code", "message"}` и тоже расходует шаг;
- программа `cmd:` получает по строке JSON на сообщение: `{"type":"reset","observation","info"}`, затем `{"type":"step","observation","reward","terminated","truncated","info"}`, в конце `{"type":"close", ...}` с последним переходом;
- на каждый эпизод раннер запускает новый процесс и создаёт новый экземпляр политики, поэтому состояние между эпизодами не переносится; для воспроизводимой случайности берите seed из аргумента и `episode_id`;
- `--policy-arg k=v` передаётся в конструктор каждой своей политики как именованный аргумент, значение разбирается как JSON, если получается (`seed=7` станет числом 7), иначе остаётся строкой; встроенные политики берут только известные им аргументы.

Python-политика реализует `reset(observation, info) -> action` и `step(observation, reward, terminated, truncated, info) -> action`. Метод `end(observation, reward, terminated, truncated, info)` необязателен. В train-режиме через него приходит терминальная награда.

Протокол JSON-строк:
- раннер шлёт политике `{"type":"reset"|"step"|"close", ...}`, а сообщение `close` несёт последний переход: награду, флаги и `info`;
- политика отвечает одним действием на строку, `{"name": ..., "arguments": {...}}`.

Пример лежит в `examples/stdio_policy.py`.

Stdout служит каналом протокола. Для Python-политик вида `module:Class` хост держит протокол в отдельном дескрипторе, поэтому `print()` и логирование безопасны и уходят в stderr. Программа `cmd:` должна писать в stdout только действия. Stderr раннер читает непрерывно, так что болтливая политика не зависает. Если политика упала, раннер печатает последние строки её stderr.

Остальные команды:
- `auditgym play`: сыграть эпизод вручную;
- `auditgym grade --episode DIR --findings f.json`: оценка с трассой сопоставления;
- `auditgym replay RUN`: повтор действий с побайтной сверкой;
- `auditgym leakscan RUN...`;
- `auditgym perturb --episode DIR --out DIR2`: копия эпизода с перестановкой и переименованием для парной проверки;
- `auditgym datacheck` и `auditgym paired`: независимая проверка данных и парные проверки на любом split, см. раздел «Проверка организаторов по разделу 06 кейса»;
- `auditgym generate`;
- `auditgym schema`: JSON Schema выводов, действий и tool-определения для LLM.

В Docker папка `/app` доступна только для чтения, поэтому `generate` и `schema` запускайте с `--out /tmp/...` или со смонтированной папкой. Конфигурацию генератор проверяет. Неизвестные ключи, перевёрнутые диапазоны, невозможные наборы валют, окно отсечения вне [4, 60] дней и `max_errors` больше 25 дают ошибку с кодом 2. Если в выбранном году и часовом поясе местное время перескакивает через день, как в Pacific/Kiritimati в 1994 году, и правильные книги не проходят инварианты или эталон не доказывается своими доказательствами, генератор эпизод не выпускает. `run_policies` не потокобезопасен, поэтому запускайте прогоны по очереди или в отдельных процессах.

Обёртка Gymnasium: `gym.make("AuditGym-v1")` после `import auditgym.contrib.gymnasium_env`, пример в `tests/test_gymnasium.py`.

## Эпизод и формат данных

Эпизод описывает одну компанию за один месяц. От эпизода к эпизоду меняются:
- базовая валюта: KZT, USD или EUR;
- одна-три иностранные валюты из USD, EUR, KZT, JPY с нулём знаков после запятой, KWD с тремя знаками, CNY, GBP;
- часовой пояс: Asia/Almaty, Asia/Tashkent, Europe/Berlin с переходом на летнее время, Asia/Dubai, UTC;
- месяц, имена, ID, порядок записей, суммы и сочетания ошибок.

В открытых эпизодах 452–1927 проводок, 65–324 документа и 0–12 ошибок. Документов бывает больше, чем в предложенном кейсом диапазоне 20–200: так выходит при настройках генератора по умолчанию из таблицы «Ключи конфигурации», на правила проверки это не влияет. Меньшие эпизоды задаются ключами `invoices` и `expenses`.

| Файл | Содержимое |
|---|---|
| `manifest.json` | `schema_version, episode_id, base_currency, period_start, period_end` (конец не включается), `timezone, export_end` (окно после периода для проверки отсечения), `counts`, `rounding`, `currency_exponents`, `amount_tolerance_minor` |
| `ledger.csv` | `row_id, timestamp, account, debit_minor, credit_minor, currency, entity_id, invoice_id, payment_id`. Суммы проводок в базовой валюте; `row_id = L-<проводка>-<строка>`; отсутствующие ссылки записаны явным `null` |
| `invoices.jsonl` | `doc_id, invoice_id, doc_type` (invoice/credit_note), `entity_id, issued_at, due_at, delivered_at, currency, total_minor, line_items, delivery_ref, service_period, ref_invoice_id` |

## Контракт среды, `auditgym/env.py`

- **Сброс.** `reset(seed, config)` возвращает `(observation, info)`. Также принимаются `options={"episode": Episode}` и `{"episode_dir": path}`. Первое наблюдение содержит задачу, manifest, политику, описание таблиц, действия, лимиты и `steps_remaining`. Seed, число ошибок и параметры конфигурации в наблюдение не попадают.
- **Шаг.** `step({"name", "arguments"})` возвращает `(observation, reward, terminated, truncated, info)`, где наблюдение имеет вид `{result, error, steps_remaining}`.
- **Действия.**
  - `list_records(table, cursor, limit≤50)`. Курсор `next_cursor` выдаёт только среда. Он стабилен в пределах эпизода и привязан к таблице. Курсор другой таблицы или эпизода и испорченный курсор дают `invalid_cursor`. Курсор кодирует только смещение, которое и так доступно через `limit`, поэтому подбирать его бесполезно.
  - `get_record(table, id)` принимает `row_id`, `doc_id` или `FX-<дата>-<SRC>-<TGT>`.
  - `get_document(doc_id)`.
  - `calculator(expression)` считает только `+ − * / ( )` над десятичными числами. Внутри обходчик AST над `Decimal`, `eval` не используется.
  - `submit(findings)`.
- **Ошибки.** Коды берутся из закрытого перечня: `unknown_action, invalid_action, invalid_arguments, unknown_table, not_found, invalid_cursor, calc_error, episode_over`. Сообщение строится по шаблону и повторяет только ввод политики, не длиннее 64 символов. Ошибка расходует шаг, но эпизод не завершает. Отдельно стоят коды завершения: `step_limit`, когда закончились 100 шагов, `time_limit`, когда кончились 60 секунд эпизода, и от раннера `timeout` (политика не ответила вовремя) и `policy_crash` (политика упала); все они дают `truncated=true` и пустой ответ. Политику, которая превысила 60 секунд, раннер останавливает на ближайшей границе шага, поэтому в логе эпизода может стоять до 62 секунд.
- **Завершение.**
  - Лимит 100 шагов, включая `submit`. Отправить ответ на сотом шаге можно.
  - Если сотое действие не `submit` или эпизод длится дольше 60 секунд, он завершается с `truncated=true` и оценивается как пустой ответ.
  - После окончания любой `step` возвращает `episode_over`. Шаг при этом не расходуется, повторной оценки нет.
- **Награда.** Промежуточная награда всегда 0. В режиме `train` политика получает терминальную награду и метрики в `info.grade`. В режиме `eval` все награды равны 0, `info` содержит только `{steps_remaining, error_code}`, а оценка остаётся в раннере до конца прогона.

## Выводы, сопоставление, награда: `auditgym/matcher.py`, `auditgym/schemas.py`

Формат ответа: `findings.json = {episode_id, findings:[{type, affected_ids, claimed_amount_minor, currency, evidence_ids, explanation}]}`.

Ответ с неверной структурой получает награду ровно −1. Лимиты: до 30 выводов, до 10 ID доказательств и до 1000 символов объяснения на вывод. Неверной структурой считаются также:
- лишние или отсутствующие поля;
- чужой `episode_id`;
- тип вне перечня;
- `true`, `1.0` или `"100"` вместо целого числа;
- отрицательная сумма или сумма больше 10¹⁸;
- `NaN`, `±Infinity` или `1e400`. В строке действия от политики это `invalid_action`, и шаг расходуется;
- валюта вне списка ISO-кодов среды;
- дубли ключей в JSON-строке политики, это тоже `invalid_action`.

Опубликованные правила. Канонические `affected_ids` задаются через `doc_id`:

| Тип | `affected_ids` | Сумма (всегда в базовой валюте) |
|---|---|---|
| `duplicate_invoice` | оригинал + дубль | дебет AR дубля |
| `payment_allocation` | платёж + недоразнесённый счёт | недокредитованная AR по курсу счёта |
| `fx_conversion` | документ | \|записанная − правильная\| базовая сумма |
| `period_cutoff` | документ | правильная базовая сумма проводки в чужом периоде (документ × курс по политике; совпадает с записанной, если неверна только дата) |

Сопоставление.
- **Условия совпадения.** Тип совпадает. Множество `affected_ids` совпадает точно, регистр, пробелы и Unicode не нормализуются. `|claimed − expected| ≤ 1` минимальная единица, при этом каждая внесённая ошибка не меньше 100 единиц. Валюта совпадает. Все ID доказательств существуют, и `evidence_ids` содержит хотя бы один допустимый набор.
- **Однозначность.** Пары (тип, affected_ids) в эталоне уникальны, поэтому каждому выводу подходит не больше одной ошибки эталона. Оценщик перебирает ошибки эталона по `issue_id`, и каждая берёт подходящий вывод с наименьшим индексом. Здесь жадный перебор даёт максимальное сопоставление, это проверяет полный перебор в `test_brute_force_matching_equivalence`. Повторы и несопоставленные выводы считаются FP с указанием причины, пропуски считаются FN.
- **Метрики и награда.** `F1 = 2TP/(2TP+FP+FN)` с граничными случаями из кейса. `reward = clip(2·F1 − 1 − 0.002·inspection_steps, −1, 1)`, где `inspection_steps` считает все шаги до `submit`, включая ошибки и калькулятор.
- **Текст объяснения оценщик не читает.**
- **Экспериментальная награда.** `reward_experimental` показывается отдельно и в общую награду не подмешивается. Верные тип и ID при неверной сумме или доказательстве дают в ней 0.5 TP, не больше одного раза на ошибку эталона. Копии ничего не приносят.

## Генератор: `world.py` → `inject.py` → `episode.py`

1. **Мир.** Сид порождает события: продажи с поставками, частичные и разбитые платежи, оплату пачкой, кредит-ноты, переплаты с возвратом, комиссии банка, авансы, начисления с разворотом и открытое сальдо AR на начало периода. Курсы строятся как сидированное случайное блуждание по рабочим дням. Все события проводятся по шаблонам проводок. Перенос курса AR и курсовые разницы на счетах 7100 и 7200 учитываются по IAS 21.
2. **Ошибки.** Каждый тип включается и считается отдельно через `config.errors.<type>`. Число `count` задаёт верхнюю границу. Если подходящей цели нет, инжектор пропускается, и это записано в `provenance.skipped_injectors`.
   - E1, дубль счёта: та же поставка `delivery_ref`, номер в другом формате или новый.
   - E2, пропущенное или частичное разнесение: кредит уходит на счёт 2150 вместо AR.
   - E3, неверная дата курса: взят курс другой даты, или курс даты счёта применён к платежу.
   - E4, отсечение: проводка попала в другой период, чем поставка.

   После внесения ошибки книги остаются сбалансированными. Расхождение видно, только если сравнить документ с проводкой или аналитику с главной книгой.
3. **Взаимодействующие сценарии.**
   - X1: частичный валютный платёж в последний день периода проведён в следующем периоде по курсу дня проводки и разнесён частично. Агент должен найти три связанных вывода: cutoff, fx и allocation.
   - X2: к валютному счёту выпущена кредит-нота, позже ту же поставку выставили повторно (дубль), а кредит-нота проведена по курсу счёта, а не по курсу своей даты. Здесь два связанных вывода.
4. **Корректные случаи, похожие на ошибки:**
   - одинаковые еженедельные подписки;
   - разбитые платежи и оплата пачкой;
   - честный остаток долга;
   - кредит-нота с оплатой нетто;
   - переплата с возвратом;
   - курсовая разница;
   - курс выходного дня;
   - поставки около полуночи, записанные в UTC;
   - поздние вечерние платежи, в том числе в последний день периода;
   - счета, выставленные через 1–3 дня после поставки;
   - комиссия банка;
   - одинаковые суммы у разных клиентов;
   - похожие номера счетов;
   - авансы без ссылок;
   - начисление с разворотом;
   - одинаковая аренда.
5. **Эталон выводится из записанного изменения.** `provenance.json` хранит инжектор, его параметры и строки до и после. ID присваиваются уже после внесения ошибок, в каноническом порядке, поэтому ни ID, ни порядок ничего не выдают.

Проверку данных делают `invariants.py` и `recheck.py`, генератор они не импортируют. Проверяется следующее:
- на правильных книгах выполняются I1–I8: баланс каждой проводки, нулевое сальдо оборотов, AR = аналитика, сумма строк счёта = итог, конвертация по политике, период, распределение, одна поставка = один счёт;
- после внесения ошибок нарушения **ровно** совпадают с объявленными ошибками и их суммами;
- **каждый** допустимый набор доказательств сам по себе воспроизводит сумму эталона.

Эти проверки идут на всех открытых эпизодах и на 40 новых сидах в каждом прогоне `check`.

## Изоляция и утечки

Раннер владеет генерацией, эталоном и оценкой. В eval-режиме политика, в том числе `cmd:`, работает дочерним процессом через `auditgym.policy_host`. Для неё действуют такие ограничения:
- окружение очищено, `AUDITGYM_SALT` в нём нет;
- рабочая директория пустая и временная;
- rlimit ограничивают CPU, память и число дескрипторов до 64, а размер записываемых файлов равен нулю. Байты записать нельзя, но пустой файл, папку или симлинк создать можно;
- `RLIMIT_NPROC=1`, поэтому политика не запустит `ps` и не оставит демона, который переживёт убийство группы. На Linux этот лимит считает и потоки. Для root лимит не действует, поэтому образ работает от пользователя `auditor`;
- чтение и запись в канал ограничены дедлайнами, 30 с на шаг и 60 с на эпизод;
- группа процессов политики убивается целиком;
- на Linux раннер делает себя non-dumpable через `PR_SET_DUMPABLE=0`, и процесс того же пользователя не прочитает `/proc/<runner>/environ`.

Флаг `--allow-forks` снимает запрет на потоки и процессы. Он нужен программам, которые без них не работают, и предназначен только для доверенных политик. На Linux раннер тогда становится subreaper. После каждого эпизода и перед записью результатов он замораживает сигналом SIGSTOP и убивает всё оставшееся дерево процессов политики. Хеши в `run.json` считаются от записанных байтов, так что уцелевший процесс может испортить папку прогона, но не подделать результат, а испорченную папку отвергнут `compare` и `replay`. Когда раннер работает как PID 1 контейнера, он убивает все остальные процессы контейнера через `kill(-1)`, включая запущенные через `docker exec`. На macOS такой гарантии нет.

Некорректная строка от политики считается `invalid_action` и расходует шаг. Сюда относятся не-JSON, дубли ключей, глубокая вложенность и одиночные суррогаты. Тайм-аут или падение дают `truncated` с пустым ответом.

Результаты и трассы раннер пишет только после того, как закончили все политики вызова, и oracle идёт последним. Каждую папку прогона он собирает заново во временной директории и подменяет ею то, что лежало по этому пути. Подложенные политикой симлинки, файлы, FIFO или закрытые папки поэтому не меняют результаты на диске, а изменённые политикой права на `--out` раннер восстанавливает. Политика того же пользователя может сорвать прогон, например сигналом раннеру, но незаметно подменить его результаты не может.

В `run.json` записаны имя папки и SHA-256 остальных файлов, это ловит подмену и переименование. В закрытом прогоне там же лежит HMAC с ключом из секретной соли, отдельно для каждого файла и для всего `run.json` с именем папки, политикой и хешами. Процесс того же пользователя может переписать байты на месте через mmap или скопировать чужую папку, но без соли не пересчитает подпись. `compare` и `replay` отказываются работать с папкой, где что-то не сходится. С заданным `-e AUDITGYM_SALT` подпись обязательна, и её отсутствие тоже считается ошибкой.

Папку `--policy-path` раннер добавляет в конец `sys.path` только для пользовательских политик и только после установки лимитов. Файлы в ней не подменяют модули стандартной библиотеки и не попадают во встроенные политики.

Перед закрытым прогоном на Linux раннер проверяет, не лежит ли значение соли в читаемом окружении или командной строке другого процесса, например при `docker --init`, `sh -c` или `uv run`. Если лежит, он отказывается стартовать.

Мир строится из `HMAC(salt, seed|config|version)`. Без соли раннера политика не восстановит эталон, даже если импортирует открытый генератор и переберёт сиды. Открытые train/dev всегда используют опубликованную соль. Eval-прогон других сидов без `AUDITGYM_SALT` завершается ошибкой, явный обход даёт флаг `--public-salt`.

Как проверяются утечки:
- `leakscan` ищет в наблюдениях и `info` ID эталона, термины оценщика, имена инжекторов, пути, трассировки и соль, а в eval-режиме ещё ненулевые награды и лишние ключи `info`;
- при пустом эталоне наблюдения и `info` совпадают побайтно, это проверяет `test_truth_swap_invariance`;
- атаки из ревью закреплены тестами в `tests/test_hardening.py`: кража соли через `/proc` и `ps`, соль у PID 1, чтение чужих результатов, демон-переписчик, подложенные симлинки, рекурсивный JSON, дубли ключей, суррогаты, зависание канала.

## Воспроизводимость

Что для этого сделано:
- у каждой стадии генерации свой поток `random.Random`. Используется только `.random()`, без `hash()` и без опоры на порядок обхода множеств;
- суммы считаются в `Decimal`;
- JSON канонический;
- `tzdata` закреплён, а `zoneinfo.reset_tzpath([])` отключает файлы часовых поясов хоста;
- зависимости закреплены в `uv.lock`;
- версии схемы и генератора записаны в manifest и provenance;
- конфигурации `configs/{train,dev,closed_example}.json` версионированы через `config_version`. Хеш и версия конфигурации записаны в `provenance.json` и `run.json`, в `run.json` ещё и хеш кода.

Тесты проверяют три вещи:
- одинаковые seed, config, версия и действия дают побайтно те же записи, переходы и награды, в том числе при разных `PYTHONHASHSEED`;
- перестановка строк вместе с биекцией ID сохраняет награду oracle и результат отображённого ответа;
- replay траекторий совпадает.

## Ограничения

- **Награда не доказывает пригодность для реального аудита.** Это программная задача на вымышленных данных. Стандарты IAS 21, IFRS 15, ISA 500 и ISA 501 мы использовали как ориентир, полной моделью они здесь не являются.
- **Общая награда кейса** осталась без изменений, и у неё есть свойства, о которых стоит знать:
  - усечение на чистых книгах даёт 0.8, так что политика, которая исчерпала лимит и промолчала, на чистых книгах получает награду;
  - при 12 ошибках экономия около 44 шагов весит примерно как один пропущенный вывод;
  - при F1 = 0 награда упирается в −1, и разницы по числу шагов уже нет.
- **Курс счёта берётся на дату выставления**, `policy.fx.rate_date`, даже если поставка была раньше. IAS 21.22 допускает такой приближённый курс, потому что счёт здесь всегда выставляется в том же периоде, что и поставка, и никогда до неё.
- **Мы сознательно не моделируем** кредиторскую задолженность, переоценку открытых позиций и платежи в валюте, отличной от валюты счёта.
- **Цели ошибок выбираются с ограничениями:**
  - одиночные ошибки E2 вносятся только в платежи в базовой валюте с единственной ссылкой;
  - одиночные ошибки E3 на счетах вносятся только в неоплаченные счета, чтобы расхождение не каскадировало;
  - эти ограничения одинаковы для всех эпизодов. Распределение целей ограничено, но агенту не раскрывается.
- **Expert доказывает, что задача решаема, но не меряет её сложность.** Политика `expert` решает эпизод по видимым записям и опубликованным правилам. LLM-агенту для того же нужно прочитать 20–45 страниц и сделать точную арифметику за 100 шагов.
- **В открытых train/dev эталон лежит на диске** в `_grader/`, и политика того же пользователя может его прочитать. Закрытую проверку запускайте в Docker с `-e AUDITGYM_SALT` и split через stdin. Тогда эпизоды генерируются в памяти раннера в порядке `episode_id`, эталон на диск не пишется, а траектория oracle сохраняется без его ответа. Не используйте `--episodes` с `_grader/`, не делайте `export` соли в общей оболочке и не давайте политике следующего вызова папку с результатами предыдущего. Хеши и HMAC в `run.json` поймают подмену результатов при проверке с солью, но чтение они не запрещают.
- **Чужие политики запускайте только в Docker.** На хосте политика может навсегда изменить установку `auditgym`, если та доступна пользователю на запись, например симлинком в `__pycache__`. Поэтому при доступной на запись установке `run` с пользовательской политикой не стартует без явного `--trust-policies`, этот флаг для своего кода. В образе пакет принадлежит root, а раннер работает как PID 1 и убивает оставшиеся процессы атомарно через `kill(-1)`.
- **Изоляция процессом того же пользователя не заменяет песочницу ядра.** Защита окружения раннера через `PR_SET_DUMPABLE` работает только на Linux. На macOS дочерний процесс может прочитать начальное окружение родителя через `sysctl`, поэтому закрытую проверку запускайте в Docker. Файлы, которые может читать пользователь, политика тоже прочитает. Сеть отключает флаг Docker `--network none`.
- **Обучение весов необязательно для кейса, но мы его провели.** Qwen3-14B, SFT через LoRA на ответах `ExpertPolicy`, Kaggle T4×2, 60 отложенных эпизодов (набор A) и 60 новых (набор B), парный бутстрап.
  - **Раунд 1:** SFT на всех находках эксперта не обогнал политику «всегда пустой ответ»: Δ = −0,12, ДИ [−0,41; +0,15]. Рост над базовой моделью шёл от исправления невалидных и ложных ответов.
  - **Раунд 2:** SFT только на тех типах ошибок, которые модель может проверить по книге, с балансом пустых ответов, обогнал пустой ответ на обоих наборах. Только дубли: +0,47 [+0,30; +0,66] на A и +0,38 [+0,23; +0,54] на B. Дубли и отсечка: +0,64 [+0,44; +0,84] на A и +0,66 [+0,48; +0,85] на B. Чистые книги модель не обвиняет.
  - **Ограничения:** курсовые ошибки и распределение оплат модель не находит, до эксперта (0,99) далеко, книги уменьшены под контекст T4. Мы пробовали четыре конфигурации по очереди и каждую выбирали после результатов предыдущей; это записано в протоколе до каждого запуска, а набор B собран заранее, чтобы проверить выбор на новых эпизодах. Вторая конфигурация раунда 2 иногда ссылается на курсы за даты, которых нет в `fx.csv`.
  - Протокол, логи и все числа лежат в `training/README.md` и `training/PROTOCOL.md`. Официальная проверка от обучения не зависит.
