# AuditGym: RL-среда для дообучения моделей финансового аудита

Воспроизводимый офлайн-симулятор для ИИ-аудитора (Genesis Hackathon, FinTech, команда tryHard).
Генератор создаёт согласованную скрытую историю вымышленной компании за один отчётный период. Затем он вносит ошибки, записывает причинное изменение и выводит эталон из этого изменения.
Агент исследует записи через узкий интерфейс инструментов и отправляет выводы с доказательствами. Оценщик вне процесса агента сопоставляет выводы с эталоном и считает общую награду кейса.

Это **среда для обучения и оценки**, а не агент, чат-бот или аудиторское заключение.

## Для жюри: старт одной командой

Ничего ставить заранее не нужно: ни Python, ни git, ни ключей, ни аккаунтов, ни GPU. Выберите то, что есть на компьютере:

| Что есть на компьютере | Команда |
|---|---|
| Node.js 16+ (`npx`) | `npx -y https://codeload.github.com/itsaibarr/auditgym/tar.gz/master` |
| macOS / Linux (только `curl`) | `curl -fsSL https://raw.githubusercontent.com/itsaibarr/auditgym/master/run.sh \| sh` |
| Linux только с `wget` (например, Ubuntu Desktop) | `wget -qO- https://raw.githubusercontent.com/itsaibarr/auditgym/master/run.sh \| sh` |
| Docker (в т.ч. Windows) | `docker build -t auditgym:1.0.0 https://github.com/itsaibarr/auditgym.git`, затем `mkdir -p auditgym-report && docker run --rm --network none --user "$(id -u):$(id -g)" -v "$PWD/auditgym-report:/report" auditgym:1.0.0 tour --out /report` (в PowerShell без `--user`, `${PWD}` вместо `$PWD`) |

Команда сама скачивает `uv` (один статичный файл закреплённой версии) в `~/.cache/auditgym`, а он — Python 3.11 и зависимости из `uv.lock`; кроме неё пишутся только кеши самого uv (`~/.cache/uv`, `~/.local/share/uv`); системный Python, PATH и профиль оболочки не трогаются. Первый запуск — 1–3 минуты (загрузка), дальше тур идёт 1–1,5 минуты, а команды стартуют за секунду. Если загрузка оборвалась — повторите ту же команду: скачанное сохраняется. Без сети после первого запуска: `npx -y --offline https://codeload.github.com/itsaibarr/auditgym/tar.gz/master <команда>`, `sh ~/.cache/auditgym/src-master/run.sh <команда>` (путь curl/wget) или собранный образ Docker. Загрузка uv проверяется по SHA-256, а оборванная загрузка ничего не оставляет — достаточно повторить команду. Проверено на «чистых» контейнерах `node:22-slim` (нет git, curl и Python) и `debian:bookworm-slim` (только curl).

По умолчанию запускается **`auditgym tour`** — весь путь проверки жюри примерно за минуту:
1. официальная проверка `auditgym check` (тесты, базовые политики, порядки наград, leakscan, парные проверки, replay), сгруппированная по критериям кейса;
2. закрытая проверка как у организаторов: новые секретные сиды и соль, 20 эпизодов (5 чистых, 5 со связанными ошибками), независимая проверка данных каждого эпизода (инварианты I1–I8 до ошибок, нарушения ровно объявленные, доказательства воспроизводят суммы), политики random / reconcile / flag_all / oracle и наш expert — таблица P, R, F1, награда, награда на чистых, шаги, время;
3. 20 парных проверок (перестановка строк и смена ID документов и строк);
4. побайтный replay с перепроверкой оценки, целостность папок прогона, leakscan;

и в конце — **итог по пяти критериям кейса** (статус каждой строки берётся только из измерений этого запуска; «Инженерию» тур не измеряет и показывает «—») и готовые команды для следующих шагов (уже с вашей командой запуска). Отчёт: `auditgym-report/report.md` и `report.json`; закрытый прогон тура подписан одноразовой солью, а его split и соль сохранены в `auditgym-report/closed/`, чтобы его можно было перепроверить командой `replay`.

### Что дальше: сценарии жюри

Ниже `auditgym` — ваша команда запуска: `npx -y https://codeload.github.com/itsaibarr/auditgym/tar.gz/master`, `sh ~/.cache/auditgym/src-master/run.sh` или `docker run --rm -i --network none -v "$PWD/out:/out" auditgym:1.0.0` (тур печатает их уже готовыми).

| Задача | Команда |
|---|---|
| Свой закрытый split: новые случайные сиды в форме организаторов (5 чистых, 5 связанных, 10 прочих); сиды и параметры можно править, ключи — в таблице ниже | `auditgym split > my_split.json` |
| Итог по критериям на **ваших** сидах | `auditgym tour --split - < my_split.json` |
| Четыре политики организаторов на вашем split, таблица P, R, F1, награда, шаги, время, падения | `auditgym run --policy random,reconcile,flag_all,oracle --split - --public-salt --out out < my_split.json` |
| Сравнить прогоны, разбивка по типам ошибок | `auditgym compare out/random out/reconcile out/flag_all out/oracle --per-type` |
| Своя политика: класс Python с `reset/step` (пример `examples/my_policy.py`) | `auditgym run --policy my_policy:LookAround --policy-path examples --split dev --out out --trust-policies` |
| Своя политика: любая программа, JSON-строки через stdin/stdout (пример `examples/stdio_policy.py`) | `auditgym run --policy "cmd:python3 /abs/path/stdio_policy.py" --split dev --out out --trust-policies` |
| Сыграть эпизод вручную / JSON Schema для LLM | `auditgym play` · `auditgym schema --out out/schema` |

Если политика не импортируется или программа не найдена, `run` сразу останавливается с понятной ошибкой (код 2); если политика упала или вышла по тайм-ауту во всех эпизодах, строка помечается в колонке `crash/timeout`, а код выхода — 1. `--trust-policies` нужен только вне Docker (установка доступна вам на запись, а оценщик работает в том же процессе). Аргументы политик: `--policy-arg key=value`, например `--policy-arg seed=7` для `random`. Программы на Node.js, Go или JVM создают потоки: на Linux им нужен `--allow-forks` (лимит процессов), на macOS — нет. В образе Docker есть только Python; для другого языка: `FROM auditgym:1.0.0` + `USER root` + `RUN apt-get update && apt-get install -y nodejs` + `USER auditor`.

**Ключи конфигурации** (в split: `base_config` и `config` у эпизода; неизвестный ключ — ошибка):

| Ключ | По умолчанию | Допустимо |
|---|---|---|
| `errors.<тип>.on`, `errors.<тип>.count` | `true`, `[0, 2]` | типы `duplicate_invoice`, `payment_allocation`, `fx_conversion`, `period_cutoff`; `count` = `[min, max]` |
| `interacting.X1`, `interacting.X2` | `0.0` | вероятность 0–1 связанного сценария |
| `max_errors` | 12 | 0–25 |
| `base_currencies` / `foreign_currencies` | `[KZT, USD, EUR]` / `[USD, EUR, KZT, JPY, KWD, CNY, GBP]` | ISO-коды среды |
| `timezones` | `[Asia/Almaty, Asia/Tashkent, Europe/Berlin, Asia/Dubai, UTC]` | любые IANA-зоны |
| `year`, `months` | 2026, 1–12 | 1971–2200, подмножество 1–12 |
| `cutoff_window_days` | 5 | 4–60 |
| `customers`, `invoices`, `opening_invoices`, `on_account`, `expenses` | `[6,16]`, `[20,70]`, `[2,6]`, `[1,3]`, `[60,260]` | `[min, max]`, до 200 / 2000 / 200 / 200 / 5000 |

## Закрытая проверка

Строгий вариант для настоящих скрытых сидов: секретная соль (≥ 32 символов) видна только раннеру, split подаётся через stdin, поэтому сидов нет ни в argv раннера, ни в смонтированных файлах. Все политики — одним вызовом, папка результатов — новая и пустая.

```bash
SALT=$(openssl rand -hex 32)   # сохраните: нужна для replay и перегенерации эпизодов; не кладите в смонтированные папки
mkdir -p out eps               # образ работает от пользователя auditor: на Linux передайте свой uid
docker run -i --rm --network none --user "$(id -u):$(id -g)" -e AUDITGYM_SALT=$SALT -v $PWD/out:/out \
    auditgym:1.0.0 run --policy random,reconcile,flag_all,oracle,my_policy:LookAround --policy-path /app/examples \
    --split - --out /out < my_split.json
# свои политики: положите модуль в ./policies и добавьте -v $PWD/policies:/policies:ro и --policy-path /policies
docker run --rm --network none -e AUDITGYM_SALT=$SALT -v $PWD/out:/out:ro auditgym:1.0.0 compare /out/random /out/reconcile /out/flag_all /out/oracle --per-type
# повтор закрытого прогона (включая oracle: его ответ восстанавливается из перегенерированного эталона)
docker run -i --rm --network none -e AUDITGYM_SALT=$SALT -v $PWD/out:/out:ro auditgym:1.0.0 replay /out/reconcile --split - < my_split.json
# эпизоды закрытого split на диск — для независимой проверки после прогона (не давайте их политике)
docker run --rm --network none --user "$(id -u):$(id -g)" -e AUDITGYM_SALT=$SALT -v $PWD/my_split.json:/s.json:ro -v $PWD/eps:/eps \
    auditgym:1.0.0 generate --split /s.json --out /eps
```

Раннер запускается напрямую: с `--init`, обёртками `sh -c` / `uv run` или солью в командной строке он откажется стартовать (соль читаема другим процессом). Закрытый eval без соли, с короткой солью, с `--seeds`/`--config` или split-файлом по пути, а также с `--episodes`, где лежит `_grader/`, завершается с кодом 2.

## Единая команда проверки

```bash
docker build -t auditgym:1.0.0 .
docker run --rm --network none --cpus 2 --memory 4g auditgym:1.0.0 check
```

Без Docker: `uv sync --extra gym && uv run auditgym check` (Python 3.11).

`check` работает без сети, GPU и платных API, 30–70 секунд при 2 CPU и 4 ГБ. Коды выхода: 0 — всё пройдено, 1 — есть провал, 2 — внутренняя ошибка. Для каждой проверки печатается строка `PASS|FAIL <id> <сек> <детали>`. Отчёт пишется в `runs/check/summary.{md,json}`, а `--json` печатает один JSON-документ. Что входит в проверку:

1. **pytest, более 530 случаев.** Контракт reset/step, данные и эталон (равенства до внесения ошибки, ровно объявленные расхождения после, независимая достаточность доказательств), атакующие ответы, воспроизводимость, изоляция.
2. **Базовые политики** на 10 train + 10 dev эпизодах в eval-режиме, каждая в отдельном дочернем процессе.
3. **Утверждённые порядки наград:** oracle = 1.0 везде; oracle > expert > reconcile > {flag_all, random} на книгах с ошибками; flag_all = −1 на чистых книгах.
4. **leakscan** всех траекторий.
5. **20 парных проверок** с перестановкой строк и переименованием ID.
6. **Детерминизм:** повторная генерация побайтно совпадает, replay траекторий совпадает.

## Как подключить свою политику

```bash
# встроенные: random | reconcile | flag_all | expert | oracle (oracle только внутри раннера)
auditgym run --policy random,reconcile,flag_all,oracle --split dev
# своя Python-политика (класс с reset/step), запускается в изолированном дочернем процессе
auditgym run --policy my_policy:LookAround --policy-path examples --split dev --trust-policies
# любая программа на любом языке, протокол JSON-строк через stdin/stdout
auditgym run --policy "cmd:python3 /abs/path/examples/stdio_policy.py" --split dev --trust-policies
# таблица сравнения: P, R, F1, возврат, экспериментальная награда, шаги, доля FP на чистых, время, падения
auditgym compare runs/oracle runs/reconcile runs/flag_all runs/random --per-type
```

Строгий закрытый прогон со своими сидами — в разделе «Закрытая проверка» выше.

Python-интерфейс политики: `reset(observation, info) -> action`, `step(observation, reward, terminated, truncated, info) -> action` и необязательный `end(observation, reward, terminated, truncated, info)`. Через `end` в train-режиме приходит терминальная награда.
Протокол JSON-строк:
- раннер → политика: `{"type":"reset"|"step"|"close", ...}`; сообщение `close` несёт последний переход (награду, флаги, `info`);
- политика → раннер: одно действие на строку, `{"name": ..., "arguments": {...}}`.

Пример — `examples/stdio_policy.py`.

Вывод политики: stdout — канал протокола. Для Python-политик (`module:Class`) хост держит протокол в отдельном дескрипторе, поэтому `print()` и логирование безопасны и уходят в stderr; программа `cmd:` должна писать в stdout только действия. Stderr раннер читает непрерывно (болтливая политика не зависает), а последние строки печатает, если политика упала.

Остальные команды:
- `auditgym play` — сыграть эпизод вручную;
- `auditgym grade --episode DIR --findings f.json` — оценка с трассой сопоставления;
- `auditgym replay RUN` — повтор действий с побайтной сверкой;
- `auditgym leakscan RUN...`;
- `auditgym perturb --episode DIR --out DIR2` — копия с перестановкой и переименованием для парной проверки;
- `auditgym generate`;
- `auditgym schema` — JSON Schema выводов, действий и tool-определения для LLM.

В Docker папка `/app` только для чтения: `generate` и `schema` запускайте с `--out /tmp/...` или со смонтированной папкой. Конфигурация проверяется: неизвестные ключи, перевёрнутые диапазоны, невозможные наборы валют, окно отсечения вне [4, 60] дней и `max_errors` больше 25 дают ошибку с кодом 2. Генератор закрыт по умолчанию: если в выбранном годе и часовом поясе местное время перескакивает через день (исторические переходы вроде Pacific/Kiritimati 1994) и правильные книги не проходят инварианты или эталон не доказывается своими доказательствами, эпизод не выпускается. `run_policies` не потокобезопасен: запускайте прогоны последовательно или в отдельных процессах.

Обёртка Gymnasium: `gym.make("AuditGym-v1")` после `import auditgym.contrib.gymnasium_env` (см. `tests/test_gymnasium.py`).

## Эпизод и формат данных

Эпизод — одна компания и один месяц. Данные варьируются:
- базовая валюта: KZT/USD/EUR;
- 1–3 иностранные валюты: USD, EUR, KZT, JPY (exp 0), KWD (exp 3), CNY, GBP;
- часовой пояс: Asia/Almaty, Asia/Tashkent, Europe/Berlin (DST), Asia/Dubai, UTC;
- месяц, имена, ID, порядок, суммы и сочетания ошибок.

Типичный размер: 400–2000 проводок, 70–340 документов, 0–12 ошибок.

| Файл | Содержимое |
|---|---|
| `manifest.json` | `schema_version, episode_id, base_currency, period_start, period_end` (конец не включается), `timezone, export_end` (окно после периода для проверки отсечения), `counts`, `rounding`, `currency_exponents`, `amount_tolerance_minor` |
| `ledger.csv` | `row_id, timestamp, account, debit_minor, credit_minor, currency, entity_id, invoice_id, payment_id`. Суммы проводок в базовой валюте; `row_id = L-<проводка>-<строка>`; отсутствующие ссылки — явный `null` |
| `invoices.jsonl` | `doc_id, invoice_id, doc_type` (invoice/credit_note), `entity_id, issued_at, due_at, delivered_at, currency, total_minor, line_items, delivery_ref, service_period, ref_invoice_id` |
| `payments.jsonl` | `doc_id, payment_id, kind` (receipt/refund), `entity_id, timestamp, currency, amount_minor, fee_minor, invoice_refs` (`null` = платёж на аванс) |
| `fx.csv` | `date, source_currency, target_currency, rate`: десятичная строка, единиц базовой валюты за 1 единицу исходной; только рабочие дни |
| `policy.json` | Выбор даты курса, «последний доступный курс не позже даты», конвертация `round_half_even(minor·rate·10^(e_base−e_doc))` один раз на документ, границы периода в зоне компании, правило распределения платежей, правило «одна поставка — один счёт», план счетов, определения выводов |
| `_grader/` | `truth.json` и `provenance.json`. Закрытые файлы оценщика; среда их не читает и в наблюдения не передаёт. Для открытых train/dev они приложены |

Время записывается в ISO-8601 со смещением; часть документов записана в UTC, поэтому граница периода требует перевода в зону компании. Деньги хранятся как целые минимальные единицы, курсы — как десятичные строки. Плавающей точки нет нигде, это проверяется тестом.

## Контракт среды (`auditgym/env.py`)

- **Сброс.** `reset(seed, config)` возвращает `(observation, info)`; также принимаются `options={"episode": Episode}` или `{"episode_dir": path}`. Первое наблюдение содержит задачу, manifest, политику, описание таблиц, действия, лимиты и `steps_remaining`. Seed, число ошибок и параметры конфигурации в наблюдение не попадают.
- **Шаг.** `step({"name", "arguments"})` возвращает `(observation, reward, terminated, truncated, info)`. Наблюдение имеет вид `{result, error, steps_remaining}`.
- **Действия:**
  - `list_records(table, cursor, limit≤50)`: курсор `next_cursor` выдаёт только среда; он стабилен в пределах эпизода и привязан к таблице, курсор другой таблицы или эпизода и испорченный курсор дают `invalid_cursor` (курсор лишь кодирует смещение, доступное и через `limit`, поэтому его вычисление ничего не даёт);
  - `get_record(table, id)`: `row_id`, `doc_id` или `FX-<дата>-<SRC>-<TGT>`;
  - `get_document(doc_id)`;
  - `calculator(expression)`: только `+ − * / ( )` над десятичными числами, обходчик AST над `Decimal`, без eval;
  - `submit(findings)`.
- **Ошибки** берутся из закрытого перечня кодов: `unknown_action, invalid_action, invalid_arguments, unknown_table, not_found, invalid_cursor, calc_error, episode_over`. Сообщение — шаблон, который повторяет только ввод политики (не длиннее 64 символов). Ошибка расходует шаг и не завершает эпизод.
- **Завершение.**
  - Лимит — 100 шагов, включая `submit`. Отправка на сотом шаге допустима.
  - Если сотое действие не `submit` или превышены 60 секунд, эпизод завершается с `truncated=true` и оценивается как пустой ответ.
  - После окончания любой `step` возвращает `episode_over`, шаг не расходуется, повторной оценки нет.
- **Награда.** Промежуточная награда всегда 0. В режиме `train` терминальная награда и метрики (`info.grade`) возвращаются политике. В режиме `eval` все награды равны 0, `info` содержит только `{steps_remaining, error_code}`, а оценка остаётся в раннере до конца прогона.

## Выводы, сопоставление, награда (`auditgym/matcher.py`, `auditgym/schemas.py`)

Формат ответа: `findings.json = {episode_id, findings:[{type, affected_ids, claimed_amount_minor, currency, evidence_ids, explanation}]}`.

**Неверная структура даёт награду ровно −1.** Лимиты: не больше 30 выводов, 10 ID доказательств и 1000 символов объяснения на вывод. Неверной структурой считаются также:
- лишние или отсутствующие поля;
- чужой `episode_id`;
- тип вне перечня;
- `true`, `1.0` или `"100"` вместо целого числа;
- отрицательная сумма или сумма больше 10¹⁸;
- `NaN`, `±Infinity` или `1e400` (в строке действия от политики это `invalid_action`, шаг расходуется);
- валюта вне списка ISO-кодов среды;
- дубли ключей в JSON-строке политики (это `invalid_action`).

**Опубликованные правила.** Канонические `affected_ids` — это `doc_id`:

| Тип | `affected_ids` | Сумма (всегда в базовой валюте) |
|---|---|---|
| `duplicate_invoice` | оригинал + дубль | дебет AR дубля |
| `payment_allocation` | платёж + недоразнесённый счёт | недокредитованная AR по курсу счёта |
| `fx_conversion` | документ | \|записанная − правильная\| базовая сумма |
| `period_cutoff` | документ | правильная базовая сумма проводки в чужом периоде (документ × курс по политике; совпадает с записанной, если неверна только дата) |

**Сопоставление.**
- **Условия совпадения.** Тип совпадает; множество `affected_ids` совпадает точно (без нормализации регистра, пробелов и Unicode); `|claimed − expected| ≤ 1` минимальная единица (все внесённые ошибки ≥ 100 единиц); валюта совпадает; все ID доказательств существуют; `evidence_ids` содержит хотя бы один допустимый набор.
- **Однозначность.** Пары (тип, affected_ids) в эталоне уникальны, поэтому каждому выводу подходит не больше одной ошибки эталона. Ошибки эталона перебираются по `issue_id`, и каждая берёт подходящий вывод с наименьшим индексом; жадный перебор здесь даёт максимальное сопоставление, это проверено перебором в `test_brute_force_matching_equivalence`. Повторы и несопоставленные выводы считаются FP с указанием причины, пропуски — FN.
- **Метрики и награда.** `F1 = 2TP/(2TP+FP+FN)` с граничными случаями из кейса. `reward = clip(2·F1 − 1 − 0.002·inspection_steps, −1, 1)`, где `inspection_steps` — все шаги до `submit`, включая ошибки и калькулятор.
- **Текст объяснения не читается.**
- **Экспериментальная награда.** `reward_experimental` показывается отдельно и в общую награду никогда не подмешивается: верные тип и ID при неверной сумме или доказательстве дают 0.5 TP, не больше одного раза на ошибку эталона; копии ничего не приносят.

## Генератор (`world.py` → `inject.py` → `episode.py`)

1. **Мир.** Сид порождает события: продажи с поставками, частичные и разбитые платежи, оплату пачкой, кредит-ноты, переплаты с возвратом, комиссии банка, авансы, начисления с разворотом, открытое сальдо AR на начало периода и курсы как сидированное случайное блуждание по рабочим дням. Все события проводятся по шаблонам проводок; перенос курса AR и курсовые разницы 7100/7200 учитываются по IAS 21.
2. **Ошибки** (каждый тип включается и считается независимо через `config.errors.<type>`; `count` — верхняя граница: если подходящей цели нет, инжектор пропускается, и это записано в `provenance.skipped_injectors`):
   - **E1** — дубль счёта: та же поставка (`delivery_ref`), номер в другом формате или новый;
   - **E2** — пропущенное или частичное разнесение: кредит уходит на 2150 вместо AR;
   - **E3** — неверная дата курса: курс другой даты или курс даты счёта применён к платежу;
   - **E4** — отсечение: проводка в другом периоде, чем поставка.

   Книги после внесения ошибки остаются сбалансированными: расхождение видно только при сравнении документа с проводкой или аналитики с главной книгой.
3. **Взаимодействующие сценарии:**
   - **X1** — частичный валютный платёж в последний день периода, проведённый в следующем периоде по курсу дня проводки и разнесённый частично. Это три связанных вывода: cutoff, fx и allocation.
   - **X2** — дубль валютного счёта, у которого есть кредит-нота, а кредит-нота проведена по курсу счёта. Это два связанных вывода.
4. **Отвлекающие случаи (корректные):**
   - одинаковые еженедельные подписки;
   - разбитые платежи и оплата пачкой;
   - честный остаток долга;
   - кредит-нота с оплатой нетто;
   - переплата с возвратом;
   - курсовая разница;
   - курс выходного дня;
   - поставки около полуночи, записанные в UTC;
   - поздние вечерние платежи, в том числе в последний день периода;
   - счета, выставленные через 1–3 дня после поставки;
   - комиссия банка;
   - одинаковые суммы у разных клиентов;
   - похожие номера счетов;
   - авансы без ссылок;
   - начисление с разворотом;
   - одинаковая аренда.
5. **Эталон выводится из записанного изменения.** `provenance.json` хранит инжектор, параметры и строки до и после. ID присваиваются уже после внесения ошибок, в каноническом порядке, поэтому ID и порядок ничего не выдают.

**Проверка данных** (`invariants.py` и `recheck.py`; генератор при этом не импортируется):
- на правильных книгах выполняются I1–I8 (баланс каждой проводки, нулевое сальдо оборотов, AR = аналитика, сумма строк счёта = итог, конвертация по политике, период, распределение, одна поставка — один счёт);
- после внесения ошибок нарушения **ровно** совпадают с объявленными ошибками и их суммами;
- **каждый** допустимый набор доказательств сам по себе воспроизводит сумму эталона.

Это проверено на всех открытых эпизодах и на 40 новых сидах в каждом прогоне `check`.

## Изоляция и утечки

- Раннер владеет генерацией, эталоном и оценкой.
- Политика в eval-режиме работает дочерним процессом через `auditgym.policy_host` (и `cmd:` тоже):
  - окружение очищено, `AUDITGYM_SALT` в нём нет;
  - рабочая директория — пустая временная;
  - заданы rlimit: CPU, нулевой размер записываемых файлов (байты записать нельзя, но создать пустой файл, папку или симлинк можно), 64 дескриптора, память и `RLIMIT_NPROC=1` (нельзя запустить `ps` или демон, переживающий убийство группы; на Linux лимит считает и потоки; `--allow-forks` снимает запрет для программ, которым нужны потоки или процессы, и предназначен для доверенных политик: на Linux раннер становится subreaper, после каждого эпизода и перед записью замораживает (SIGSTOP) и убивает всё оставшееся дерево процессов политики, а хеши в `run.json` берутся от записанных байтов, поэтому уцелевший процесс может лишь испортить папку (её отвергнут `compare`/`replay`), но не подделать результат; когда раннер — PID 1 контейнера, он убивает все остальные процессы контейнера (`kill(-1)`), включая запущенные через `docker exec`; на macOS такой гарантии нет; для root лимит не действует, поэтому образ работает от пользователя `auditor`);
  - чтение и запись в канал ограничены дедлайнами: 30 с на шаг, 60 с на эпизод;
  - группа процессов убивается целиком;
  - на Linux раннер делает себя non-dumpable (`PR_SET_DUMPABLE=0`), и процесс того же пользователя не прочитает `/proc/<runner>/environ`.
- Некорректная строка от политики (не JSON, дубли ключей, глубокая вложенность, одиночные суррогаты) считается `invalid_action` и расходует шаг. Тайм-аут или падение дают `truncated` с пустым ответом.
- **Все** результаты и трассы пишутся только после завершения всех политик вызова; oracle запускается последним. Каждая папка прогона собирается заново во временной директории и подменяет то, что лежало по этому пути, поэтому подложенные политикой симлинки, файлы, FIFO или закрытые папки не меняют результаты на диске; права на `--out`, изменённые политикой, восстанавливаются. Политика того же пользователя может сорвать прогон (например, сигналом раннеру), но не подменить его результаты незаметно. В `run.json` записаны имя папки и SHA-256 остальных файлов (ловят подмену файлов и переименование), а в закрытом прогоне ещё и HMAC с ключом из секретной соли — для каждого файла и подпись всего `run.json` (имя папки, политика, хеши): процесс того же пользователя может переписать байты на месте (mmap) или скопировать чужую папку, но не может пересчитать подпись без соли. `compare` и `replay` отказываются работать с папкой, где что-то не сходится; с заданным `-e AUDITGYM_SALT` подпись обязательна (её отсутствие тоже ошибка).
- Папка `--policy-path` добавляется в конец `sys.path` только для пользовательских политик и только после установки лимитов, поэтому файлы в ней не подменяют модули стандартной библиотеки и не попадают во встроенные политики.
- Перед закрытым прогоном на Linux раннер проверяет, что соль не лежит в читаемом окружении другого процесса (`docker --init`, `sh -c`, `uv run`), иначе отказывается стартовать.
- **Соль:** мир строится из `HMAC(salt, seed|config|version)`. Без соли раннера политика не восстановит эталон, даже если импортирует открытый генератор и переберёт сиды. Открытые train/dev всегда используют опубликованную соль; eval-прогон других сидов без `AUDITGYM_SALT` завершается ошибкой (явный обход: `--public-salt`).
- **Проверки утечек:**
  - `leakscan` ищет в наблюдениях и `info` ID эталона, термины оценщика, имена инжекторов, пути, трассировки и соль, а также ненулевые награды и лишние ключи `info` в eval-режиме;
  - инвариантность к подмене эталона: при пустом эталоне наблюдения и `info` побайтно совпадают (`test_truth_swap_invariance`);
  - атаки из ревью (кража соли через `/proc` и `ps`, соль у PID 1, чтение чужих результатов, демон-переписчик, подложенные симлинки, рекурсивный JSON, дубли ключей, суррогаты, зависание канала) закреплены тестами в `tests/test_hardening.py`.

## Воспроизводимость

Обеспечивается так:
- отдельные потоки `random.Random` на каждую стадию; используется только `.random()`, без `hash()` и без порядка обхода множеств;
- `Decimal`;
- канонический JSON;
- закреплённый `tzdata` (`zoneinfo.reset_tzpath([])`: файлы часовых поясов хоста не используются);
- зависимости закреплены в `uv.lock`;
- версия схемы и генератора в manifest и provenance;
- версионированные конфигурации `configs/{train,dev,closed_example}.json` (`config_version`); в `provenance.json` и `run.json` записаны хеш и версия конфигурации, в `run.json` ещё и хеш кода.

Тесты проверяют три вещи:
- одинаковые seed, config, версия и действия дают побайтно те же записи, переходы и награды, в том числе при разных `PYTHONHASHSEED`;
- перестановка строк вместе с биекцией ID сохраняет награду oracle и результат отображённого ответа;
- replay траекторий совпадает.

## Честные ограничения

- **Награда не доказывает пригодность для реального аудита.** Это программная задача на вымышленных данных; стандарты (IAS 21, IFRS 15, ISA 500/501) использованы как ориентир, а не как полная модель.
- **Свойства общей награды кейса** (мы их не меняли):
  - усечение на чистых книгах даёт 0.8, поэтому молчание политики, исчерпавшей лимит, на чистых книгах вознаграждается;
  - при 12 ошибках экономия около 44 шагов весит примерно как один пропущенный вывод;
  - при F1 = 0 награда упирается в −1, и градиента по шагам нет.
- **Курс счёта — на дату выставления** (`policy.fx.rate_date`), даже если поставка была раньше: это допустимый по IAS 21.22 приближённый курс, потому что счёт всегда выставляется в том же периоде, что и поставка, и никогда до неё.
- **Сознательно не моделируется:** кредиторская задолженность, переоценка открытых позиций и платежи в валюте, отличной от валюты счёта.
- **Ограничения выбора целей и прочие допущения:**
  - Одиночные ошибки E2 вносятся только в платежи в базовой валюте с единственной ссылкой.
  - Одиночные ошибки E3 на счетах вносятся только в неоплаченные счета, чтобы расхождение не каскадировало.
  - Эти ограничения задокументированы и одинаковы для всех эпизодов; распределение целей ограничено, но не раскрывается.
  - Политика `expert` решает задачу по видимым записям, используя опубликованные правила. Это доказательство разрешимости, а не мерило сложности для LLM-агента: агенту нужно прочитать 20–45 страниц и сделать точную арифметику в пределах 100 шагов.
- **Для открытых train/dev эталон лежит на диске** (`_grader/`), и политика того же пользователя может его прочитать. Закрытую проверку запускайте в Docker с `-e AUDITGYM_SALT` и split через stdin: эпизоды генерируются в памяти раннера в порядке `episode_id`, эталон на диск не пишется, а траектория oracle сохраняется без его ответа. Не используйте `--episodes` с `_grader/`, не делайте `export` соли в общей оболочке и не давайте политике следующего вызова папку с результатами предыдущего (подмену результатов поймают хеши и HMAC в `run.json` при проверке с солью, но чтение они не запрещают).
- **Чужие политики — только в Docker.** На хосте политика может навсегда изменить установку `auditgym`, доступную пользователю на запись (например, симлинком в `__pycache__`); поэтому при доступной на запись установке `run` с пользовательской политикой отказывается стартовать без явного `--trust-policies` (для своего кода). В образе пакет принадлежит root, а раннер — PID 1 (оставшиеся процессы убиваются атомарно через `kill(-1)`).
- **Изоляция процессом того же пользователя — не песочница ядра.** Защита окружения раннера (`PR_SET_DUMPABLE`) работает только на Linux; на macOS дочерний процесс может прочитать начальное окружение родителя через `sysctl`, поэтому закрытую проверку запускайте в Docker. Читаемые пользователем файлы политика читать может. Сеть отключается флагом Docker `--network none`.
- **Обучение весов (необязательно).** Qwen3-14B, SFT (LoRA) на ответах `ExpertPolicy`, Kaggle T4×2, 60 отложенных эпизодов (набор A) плюс 60 новых (набор B), парный бутстрап.
  - **Раунд 1:** SFT на всех находках эксперта не обогнал политику «всегда пустой ответ»: Δ = −0,12, ДИ [−0,41; +0,15]. Рост над базовой моделью шёл от исправления невалидных и ложных ответов.
  - **Раунд 2:** SFT только на тех типах, что модель может проверить по книге, с балансом пустых ответов, обогнал пустой ответ на обоих наборах. Только дубликаты: +0,47 [+0,30; +0,66] на A и +0,38 [+0,23; +0,54] на B. Дубликаты и отсечка: +0,64 [+0,44; +0,84] на A и +0,66 [+0,48; +0,85] на B. Ложных обвинений чистых книг нет.
  - **Ограничения:** курсовые ошибки и распределение оплат модель не находит, до эксперта (0,99) далеко, книги уменьшены под контекст T4.
  - Протокол (предрегистрация до каждого запуска), логи и все числа — `training/README.md`, `training/PROTOCOL.md`; официальная проверка от этого не зависит.
