# Протокол эксперимента (зафиксирован до основного запуска)

Коммит с этим файлом сделан **до** запуска ядра `gag-base-sft`. Изменения после запуска фиксируются отдельным разделом «Отклонения» в README.

**Гипотеза.** Qwen3-14B после QLoRA SFT на отфильтрованных по награде траекториях эксперта (after) получает более высокую среднюю награду кейса на отложенных эпизодах, чем та же модель без дообучения (base).

**Первичная метрика.** Средняя награда кейса `reward` из грейдера среды (`AuditEnv("eval")`, `env.result()`), по 60 отложенным эпизодам.
**Вторичные.** Средний F1 по эпизодам, micro-F1, доля ответов с ошибкой схемы (`valid=false`, награда −1), доля нераспознанных ответов, шаги, доля чистых книг с ложным обвинением; разрез clean / single / multi.

**Эпизоды.** Семейство конфигов `training/episodes.py` (маленькие книги, одна иностранная валюта).
- Отложенные: 60 сидов начиная с 500000 (12 clean, по 6 на каждый одиночный тип, 12 mixed, 6 X1, 6 X2), sha256 `heldout.jsonl` = `6a96ea3eb71c42048cdb99de154b20d6ab835f744b324f9ab74e8bb80dffd647`; список сидов в `data_manifest.json`.
- SFT: сиды 100000–100590 (не пересекаются с отложенными и с `configs/train.json` 101–110, `configs/dev.json` 201–210, `configs/closed_example.json` 9000+). sha256 `sft.jsonl` = `7345414d010578f84a16496d1d6a3a6325339edfbf6c7ee2cc580d286019dc66`.
- Ограничение контекста: эпизоды с промптом > 5 632 токенов пропускаются (правило смотрит только на публичную рабочую книгу; сколько пропущено, указано в `data_manifest.json`).

**Политика (одинаковая для обоих плеч).** Скаффолд читает все страницы fx, invoices, payments, ledger (`list_records`, limit 50: 6–8 шагов), рендерит наблюдённые строки в компактную рабочую книгу, модель один раз отвечает JSON `{"findings": [...]}`, скаффолд добавляет `episode_id` и отправляет объект как есть. Никакой починки, кроме удаления code fence и выделения внешних `{...}`. Ошибка схемы оценивается средой (−1).

**Модель и декодирование.** `unsloth/Qwen3-14B-bnb-4bit` @ `b455922269e4678c84f854fe38a6993d73614a1e` (NF4, вычисления в fp16), шаблон чата Qwen3 с `enable_thinking=False`, greedy, `max_new_tokens=1024` (ответ, обрезанный на лимите, обычно не является валидным JSON и получает −1, одинаково для обоих плеч), батч 2 с левым паддингом, точное внимание по блокам запросов (512), Kaggle T4.

**Обучение.** LoRA r=16, alpha=32, dropout 0, q/k/v/o/gate/up/down; AdamW lr 1e-4, warmup 3 шага, косинус; накопление 8; один проход по всем 400 примерам `sft.jsonl` в порядке сидов (50 шагов оптимизатора); лосс только на токенах ответа; fp16 autocast, адаптер в fp32; модель разнесена на две T4 (слои 0–19 / 20–39); остановка по времени через 15 000 с (если сработает, число реально пройденных примеров записывается в `train_meta.json`). Учитель: `ExpertPolicy` (без доступа к истине); фильтр: награда эксперта ≥ 0.5. Истина используется только для фильтра.

**Статистика.** Парный перцентильный бутстрап по эпизодам, Δ = after − base, 10 000 повторов, seed 20261121, 95% ДИ. Также победы/ничьи/поражения.

**Правило вывода.** Писать «SFT улучшает награду на отложенных эпизодах» только если нижняя граница 95% ДИ для Δ средней награды > 0. Если ДИ содержит 0: «значимой разницы нет (Δ = x, 95% ДИ [a, b], n = 60)». Если верхняя граница < 0: «SFT ухудшает». Число опробованных конфигураций обучения: 1. Любой повторный запуск указывается в README.

**Калибровка (smoke, до протокола).** `gag-smoke` v1 упал по памяти (полная матрица внимания SDPA, батч 3), v2 прошёл: шаг SFT ≈ 48 с на пример 6,1k токенов на двух T4, пик 8,3/8,6 ГБ; на одной T4 обучение не помещается; генерация батча 2 — 133–293 с. Результаты smoke генерации в выводы не входят.

## Дополнение 1 (2026-11-20 06:05, до запуска `gag-sft2`): вторая конфигурация

Результат конфигурации 1 уже известен: after на всех 60 эпизодах отвечает `{"findings": []}`. Диагностика (`gag-diag`) показала причину. Это ошибка нормировки лосса, а не свойство данных. Лосс усреднялся внутри каждого примера, затем делился на 8, поэтому развилочный токен ` []` / ` [{"` в коротком пустом ответе (7 токенов) весил примерно в 35 раз больше, чем в длинном. Модель выучила P(пусто) ≈ 0,86 почти независимо от входа, при 31% пустых целей.

**Конфигурация 2** отличается только одним: сумма CE по токенам группы накопления делится на число токенов ответа в группе (`GAG_LOSS_NORM=token_sum`). Данные, порядок, гиперпараметры, остановка по времени и декодирование те же. Base-генерации переиспользуются: базовая модель и промпты те же.

Первичный результат остаётся за конфигурацией 1. Конфигурация 2 сообщается отдельно, с тем же правилом вывода (бутстрап after2 − base, n = 60) и с явной пометкой, что опробовано 2 конфигурации. Других конфигураций не будет: бюджет GPU.

## Дополнение 2 (2026-11-20 16:50, до запуска `arttts/gag3-sft`): конфигурация 3, раунд 2

**Что известно на момент записи.** В раунде 1 ни одна конфигурация не обогнала политику «всегда пустой ответ» на наборе A (`heldout.jsonl`, 60 эпизодов). Поэтому ниже добавлен новый набор B.

- Цель = находки `ExpertPolicy` типа `duplicate_invoice`; находки других типов отброшены. Если дубликатов нет, цель `{"findings": []}`.
- 640 примеров: 320 с непустой целью и 320 с пустой (102 из них чистые книги), чередуются через один. Сиды обучения 100000–101599. Фильтр по награде эксперта ≥ 0,5. sha256 `sft3.jsonl` = `fa2d45f2cd855407efbeb3eb73ff47fd004efb5192745ffe08ab6ea074fdd2a7`.
- Промпт, рендер книги, модель, LoRA (r=16, alpha=32, 7 проекций), lr 1e-4, косинус, warmup 3, накопление 8 и декодирование — как в раунде 1.
- Нормировка лосса: token-sum, как в конфигурации 2. Один проход по 640 примерам, остановка по времени 28 800 с.
- Аккаунт Kaggle `arttts`, ядра `gag3-sft` и `gag3-eval`.

**Наборы для оценки.**
- **A** (первичный): те же 60 эпизодов, что в раунде 1. Base-ответы на A берутся из раунда 1: та же модель, промпт, декодирование и тип GPU.
- **B** (подтверждающий): 60 новых эпизодов с сидов 600000, та же квота профилей и то же правило длины. Собран до появления любых результатов конфигурации 3, никогда не использовался для решений. sha256 `heldout_b.jsonl` = `9bd1edaf2dd3e46786a6d7cac4b28250f6c3628688356572faa312ff8f29f499`. На B генерируются c3 и base.

**Гипотеза H3.** Средняя награда c3 выше, чем у политики «всегда пустой ответ», на наборе A.

**Статистика.** Как раньше: парный перцентильный бутстрап, 10 000 повторов, seed 20261121. Сравнения: c3 − пусто и c3 − base, на A и на B.

**Правило вывода.**
- «Конфигурация 3 лучше тривиального пустого ответа» пишется только если нижняя граница 95% ДИ для (c3 − пусто) > 0 на A.
- Если на B ДИ содержит 0, это сообщается как «не воспроизвелось на новых сидах».
- Слово «улучшает» без оговорок — только если ДИ > 0 и против пустого ответа, и против base, на A и на B.
- Если ДИ на A содержит 0: «значимой разницы с пустым ответом нет».
