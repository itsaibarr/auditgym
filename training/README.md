# Дообучение LLM на AuditGym: Qwen3-14B до и после SFT (Kaggle T4)

Небольшой контролируемый эксперимент. Он не входит в `auditgym check`, не меняет среду и не нужен для её проверки. Всё лежит в `training/`.

## Итог

Отложенные эпизоды: n = 60 (сиды 500000+, не пересекаются с SFT и с `configs/`). Оценка: грейдер среды, eval-режим, награда кейса. Парный перцентильный бутстрап по эпизодам, 10 000 повторов.

| Плечо | Средняя награда | Средний F1 | micro-F1 | TP / FP / FN | Ошибка схемы (−1) | Нераспознано | Шаги | Ложные обвинения на чистых книгах |
|---|---|---|---|---|---|---|---|---|
| **base** (Qwen3-14B без дообучения) | **−0,983** | 0,009 | 0,018 | 2 / 119 / 100 | 53,3% | 3,3% | 6,9 | 75% |
| **after, конфигурация 1** (предрегистрирована) | **−0,470** | 0,267 | 0,000 | 0 / 0 / 102 | 0% | 0% | 6,9 | 0% |
| **after2, конфигурация 2** (token-sum лосс) | **−0,591** | 0,206 | 0,157 | 18 / 109 / 84 | 1,7% | 1,7% | 6,9 | 75% |
| справка: всегда пустой ответ | −0,470 | 0,267 | 0,000 | 0 / 0 / 102 | 0% | 0% | 6,9 | 0% |
| справка: `ExpertPolicy` (без истины, та же книга) | 0,988 | 1,000 | 1,000 | 102 / 0 / 0 | 0% | 0% | 6,9 | 0% |

| Сравнение (Δ средней награды) | Δ | 95% ДИ | победы / ничьи / поражения |
|---|---|---|---|
| after (конф. 1) − base | +0,514 | [+0,298, +0,751] | 16 / 42 / 2 |
| after2 (конф. 2) − base | +0,392 | [+0,236, +0,567] | 19 / 41 / 0 |
| after2 (конф. 2) − всегда пустой ответ | −0,121 | [−0,410, +0,155] | 16 / 31 / 13 |

**Как это читать.**

1. **Формально правило вывода выполнено для обеих конфигураций:** нижняя граница ДИ для Δ = after − base больше 0. Но рост награды не означает, что модель научилась аудиту.
2. **Конфигурация 1 (предрегистрированная) выродилась.** На всех 60 эпизодах дообученная модель отвечает `{"findings": []}`. Её результат побайтно совпадает с тривиальной политикой «ничего не находить». Весь выигрыш у base берётся из двух вещей: модель перестала обвинять чистые книги и перестала ломать схему. Ни одной найденной ошибки. Причина — дефект нормировки лосса в моём обучающем цикле (подробно ниже).
3. **Конфигурация 2** (дефект исправлен, остальное то же) действительно находит ошибки: 18 TP против 2 у base. Почти всё это дубликаты счетов (17 из 29 при 2 FP). По fx_conversion, period_cutoff и payment_allocation модель почти ничего не находит и много выдумывает: 79 FP на fx. На чистых книгах она обвиняет в 9 из 12 случаев. **От политики «всегда пусто» конфигурация 2 статистически не отличается:** Δ = −0,12, 95% ДИ [−0,41, +0,16]. Она лучше пустого ответа на книгах с несколькими ошибками (+0,39 [+0,09, +0,65], n = 24) и хуже на чистых (−1,49, n = 12).
4. **Вывод:** SFT на отфильтрованных траекториях эксперта значимо поднимает награду Qwen3-14B относительно базовой модели (n = 60). Но ни одна дообученная модель не превосходит значимо тривиальный пустой ответ. До эксперта (0,99) очень далеко. Опробовано 2 конфигурации обучения, вторая после того, как стал известен результат первой. Это раскрыто в `PROTOCOL.md`, дополнение 1.

**Разрез по группам (средняя награда; base → after → after2).** clean (n = 12): −1,000 → +0,989 → −0,503. Одна ошибка (n = 24): −1,000 → −0,752 → −0,696. Несколько ошибок, mixed/X1/X2 (n = 24): −0,958 → −0,917 → −0,530.

**По типам ошибок (TP / FP / FN, только валидные ответы).**

| | base | after2 |
|---|---|---|
| duplicate_invoice | 2 / 12 / 6 | **17 / 2 / 12** |
| fx_conversion | 0 / 42 / 9 | 0 / 79 / 27 |
| payment_allocation | 0 / 26 / 8 | 1 / 16 / 18 |
| period_cutoff | 0 / 39 / 10 | 0 / 12 / 27 |

У base FN меньше только потому, что 32 его ответа из 60 невалидны и в разбивку по типам не попадают.

### Почему базовая модель получает −1

- 30 из 32 невалидных ответов base — пропущенное поле `explanation`. Оно показано в формате ответа в системном промпте, но это обязательное поле схемы. Ещё 2 ответа — JSON, обрезанный на лимите 1 024 токенов.
- Исследовательская строка, не предрегистрированная: если дописать пустое `explanation`, base получает −0,931 и обвиняет 100% чистых книг. Дело не только в формате.
- Почти все FP базовой модели — находки без соответствующей ошибки (113 из 119, причина `no_issue` в трассе грейдера).

### Почему конфигурация 1 выродилась (диагностика `gag-diag`)

- Teacher-forced на отложенных эпизодах дообучение сильно приблизило модель к эксперту: NLL на токен ответа эксперта 0,83 → 0,09, совпадение greedy-токенов 0,89 → 0,97.
- Но весь ответ решается одним развилочным токеном: ` []` («пусто») против ` [{"` («начать находку»). На всех 44 отложенных эпизодах с ошибками и на всех 14 виденных при обучении модель ставит на ` []` около 0,86. Это почти не зависит от входа, хотя пустых целей в данных 31% (121 из 392).
- Причина в нормировке. CE усреднялся внутри примера, затем делился на 8. Развилочный токен в пустом ответе (7 токенов) весил около 1/7, в длинном ответе (~250 токенов) — около 1/250. Взвешенный оптимум на развилке ≈ 0,94 «пусто».
- Fp32-адаптер (v1, 34 эпизода) даёт тот же пустой ответ, так что это не артефакт приведения адаптера к fp16.
- Конфигурация 2 нормирует сумму CE на число токенов ответа в группе накопления, и коллапс исчезает.

## Постановка

- **Модель:** Qwen3-14B (`unsloth/Qwen3-14B-bnb-4bit` @ `b455922`, NF4, вычисления fp16), режим без размышлений (`enable_thinking=False`), greedy.
- **Плечи:** *base*: модель без дообучения; *after*: та же модель + LoRA-адаптер после SFT. Скаффолд, промпт, эпизоды, декодирование и железо одинаковые.
- **Оценка:** собственный грейдер среды. Каждый ответ модели проигрывается через свежий `AuditEnv("eval")`: те же шаги чтения, затем `submit`, затем `env.result()`. Метрики: награда кейса, F1, ошибки схемы, шаги.
- **Протокол** зафиксирован в [`PROTOCOL.md`](PROTOCOL.md) и закоммичен до основного запуска.

### Политика-скаффолд (`agpolicy.py`)

1. `reset`, затем `list_records(limit=50)` по всем страницам fx, invoices, payments, ledger. Это те же действия, что у встроенного `ExpertPolicy`, 6–8 шагов.
2. Наблюдённые строки рендерятся в компактную текстовую «рабочую книгу». Это только форматирование, без сверок и джойнов. Не печатаются: курсы старше первой даты документа минус 7 дней; зеркальные проводки выручки и возвратов 4000/4100 (они повторяют проводку по AR); проводки только по расходам.
3. Модель отвечает один раз: `{"findings": [...]}`.
4. Скаффолд добавляет `episode_id` и отправляет объект как есть. Ошибку схемы оценивает среда, награда −1.

Проверка паритета: если отправить через скаффолд сериализованный ответ эксперта, награда совпадает с наградой самого эксперта на всех 60 эпизодах.

### Эпизоды и данные (`episodes.py`, `make_data.py`, `data_manifest.json`)

- Свои маленькие конфиги: 2–3 клиента, 2–5 обычных счетов плюс встроенные дистракторы генератора, одна иностранная валюта на эпизод. Профили: clean, по одному типу ошибки, mixed, X1, X2.
- **Отложенные эпизоды:** 60 сидов начиная с 500000 (12 clean, по 6 на каждый одиночный тип, 12 mixed, 6 X1, 6 X2).
- **SFT:** сиды 100000–100590. Пересечений нет ни между собой, ни с `configs/train.json`, `configs/dev.json` и `closed_example`.
- **Ограничение контекста:** промпт ≤ 5 632 токенов, ответ ≤ 1 024 токенов. Эпизоды с более длинной книгой пропускаются по правилу, которое смотрит только на публичную книгу: 27 отложенных и 191 обучающий кандидат. Чаще всего пропускаются X1, X2 и mixed. Поэтому набор смещён к более коротким книгам.
- **Учитель:** встроенный `ExpertPolicy`, решатель без доступа к истине. Это фильтрованное клонирование поведения, один раунд expert iteration: эпизод попадает в SFT, только если награда эксперта по грейдеру ≥ 0.5. Отсеяно 0 из 400, потому что эксперт решает эти книги почти идеально. Оракул (истина) не клонируется.

### Обучение (`kaggle/gag_kaggle.py`)

- QLoRA: r=16, alpha=32, все 7 проекций, lr 1e-4, косинус, warmup 3, накопление 8, AdamW, адаптер fp32, autocast fp16.
- Один проход по 400 примерам; остановка по времени (15 000 с) сработала на 392 примерах (49 шагов) в обеих конфигурациях. Лосс считается только на токенах ответа: голова LM применяется только к позициям ответа. Нормировка: конфигурация 1 — среднее CE по примеру, затем /8; конфигурация 2 — сумма CE по группе накопления, делённая на число токенов ответа в группе.
- Модель разнесена на две T4: слои 0–19 на одной, 20–39 и голова на другой.
- Внимание считается точно, по блокам запросов по 512. Штатный SDPA на стеке Kaggle (torch 2.11, transformers 5.20.2) материализует полную матрицу L×L и падает по памяти. Эквивалентность проверена на CPU.
- GRPO не пробовали, обоснование в `research/06-kaggle-9b-training-plan.md` §3.3.

## Ограничения и оговорки

- **Маленькие книги.** Эпизоды намного меньше официальных конфигов: 2–3 клиента, одна иностранная валюта, промпт ≤ 5 632 токенов. Около трети кандидатов пропущено по длине, чаще X1, X2 и mixed. Результат не переносится на официальные `configs/train.json` и `dev.json`.
- **Одношаговое решение.** Навигацию делает скрипт, одинаковый для обоих плеч и совпадающий с действиями `ExpertPolicy`; модель принимает одно решение — `submit`. Поэтому шаги одинаковые: 6,9 в среднем, это скан плюс submit. Это проверка способности модели находить ошибки по полной книге, а не многошагового агента.
- **Без лимита времени.** Ответы генерируются на GPU заранее и проигрываются через среду. Поэтому `AuditEnv(time_limit_s=None)`: 60-секундный лимит кейса не применяется, на T4 генерация занимает 30–290 с на батч.
- **Обрезка ответа.** `max_new_tokens = 1024`; обрезанный ответ не является JSON и получает −1. Это 2 эпизода у base и 1 у after2.
- **Численная мелочь.** Батч 2 с левым паддингом в fp16; greedy-ответ при батче 1 может отличаться в отдельных токенах. Настройка одинакова для обоих плеч.
- **Адаптер.** Адаптер обучен в fp32, при генерации приведён к fp16: fp32 не помещался в память при промпте 5,6k × 2. Результат конфигурации 1 воспроизведён на 34 эпизодах и с fp32-адаптером.
- **Множественность.** Опробовано 2 конфигурации обучения, вторая выбрана после просмотра результата первой (раскрыто до её запуска). Других вариантов, сидов или промптов не перебиралось. Нужно n = 60, мощность умеренная: ширина ДИ около ±0,15–0,3.
- **Это не RL.** Это один раунд фильтрованного клонирования поведения (SFT на траекториях эксперта, отобранных по награде среды). Фильтр ничего не отсеял: эксперт решает эти книги почти идеально, награда ≥ 0,98. GRPO не пробовали.
- **Учитель — `ExpertPolicy`, а не оракул.** Истина используется только в фильтре по награде на обучающих сидах. Ответы эксперта на отложенных эпизодах используются только в диагностике (`gag-diag`), не в обучении.
- **Цифры GPU-часов** взяты из `kaggle quota` и округлены сервисом. Неудачные запуски (smoke v1, after v1) включены.

## Воспроизведение

```bash
uv run --with tokenizers python training/make_data.py      # детерминированно, sha256 в data_manifest.json
python3 training/kaggle/build.py                            # приватный датасет + папки ядер в training/kaggle/build/
kaggle datasets create -p training/kaggle/build/pkg -r zip  # приватный
kaggle kernels push -p training/kaggle/build/gag-base-sft --accelerator NvidiaTeslaT4 -t 23400
kaggle kernels push -p training/kaggle/build/gag-after    --accelerator NvidiaTeslaT4 -t 7200
kaggle kernels output itsaibarr/gag-base-sft -p training/results/kaggle/base   # gag-after -> results/kaggle/after
# конфигурация 2: gag-sft2 (-t 16800), затем gag-after2 -> results/kaggle/after2; диагностика: gag-diag -> results/kaggle/diag
uv run python training/grade.py                             # -> results/metrics.json, results/episodes.jsonl
```

## Файлы

- `agpolicy.py`: скаффолд (скан, рендер, разбор ответа); `play.py`: эпизод через среду; `episodes.py`: конфиги и сиды.
- `make_data.py`: отложенный набор и SFT-набор; `data_manifest.json`: сиды, sha256, статистика пропусков.
- `kaggle/gag_kaggle.py`: GPU-задание (smoke / base+SFT / after); `kaggle/build.py`: сборка датасета и ядер.
- `grade.py`: оценка грейдером среды и парный бутстрап; `results/`: генерации, логи и freeze с Kaggle, `metrics.json`, `episodes.jsonl`, `quota.log`.
- `results/per_type.json`: TP/FP/FN по типам; `results/kaggle/diag/`: teacher-forced диагностика.
- `PROTOCOL.md`: предрегистрация и дополнение 1.
