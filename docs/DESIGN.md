# Записка о дизайне AuditGym

## Задача
Сделать среду, на которой можно дообучать и оценивать ИИ-аудитора, а не самого аудитора. Жюри оценивает корректность среды и оценщика, а не награду нашего агента. Поэтому весь дизайн подчинён трём свойствам:
1. Эталон должен быть верен: генератор строит его из записанного изменения, а независимый проверщик пересчитывает каждую ошибку по записям.
2. Награду должно быть трудно обмануть: защиты ниже проверены атакующими тестами, но это не доказательство на всех возможных ответах.
3. Эпизоды воспроизводимы: одинаковые seed, конфигурация, версия и действия дают те же записи и награды, это проверяет повтор.

## Конвейер
```
seed + config + salt ──HMAC──► key
  world.build_world(key)        события → проводки по шаблонам (правильные книги)
  inject.plan(...)              prepare: легитимные документы сценариев X1/X2 (с правильными проводками)
  ── снимок правильных книг ──► clean_public (для проверки I1–I8)
  inject.mutate(...)            E1–E4, X1, X2 меняют записанные книги; Issue = тип, документы, сумма, наборы доказательств
  episode._assign_ids           ID после внесения ошибок, в каноническом порядке времени
  episode._export_public        manifest, policy, ledger, invoices, payments, fx
  truth.json / provenance.json  выводятся из Issue (строки до и после, инжектор, параметры)
```

## Как обеспечена и проверена верность эталона
- **Документы истинны, ошибаются только проводки.** Исключение — E1, где лишним является сам документ-дубль. Каждая ошибка нарушает ровно один именованный инвариант на ровно объявленную сумму. Это проверяет независимый проверщик `invariants.py`, который читает только видимые файлы.
- **Книги остаются сбалансированными:** проводки с ошибкой перебалансируются через тот счёт, который задела бы настоящая ошибка (7100/7200, 2150). Трюк «оборотка не сходится» не работает.
- **Достаточность доказательств.** `recheck.py` пересчитывает сумму каждой ошибки эталона из записей одного набора доказательств и правил политики. Набор не опирается на недоступные факты: курс нужной даты лежит в `fx.csv`, дата поставки — в документе, правило — в `policy.json`.
- **Однозначность:**
  - ключ (тип, affected_ids) уникален;
  - суммы ошибок не меньше 100 при допуске 1;
  - «дубль» — счёт, выставленный позже, а не тот, у которого лексикографически больше ID;
  - в X1 и X2 суммы не пересчитываются дважды: каждый связанный вывод измеряется относительно правильного значения остальных измерений. В X1 сумма cutoff — правильная базовая сумма платежа, а курсовая разница целиком принадлежит выводу fx; ошибка курса в X2 перенесена на кредит-ноту, потому что дубль недействителен целиком.
- **Сложные места закреплены правилами политики:** выходные дни (последний курс не позже даты), окно после периода для позднего отсечения, правило распределения платежей, «одна поставка — один счёт».

## Пересчёт вручную: по одному примеру на тип ошибки

Каждую сумму эталона можно получить из записей одного набора доказательств и правил `policy.json`, без генератора. Ниже по одному реальному примеру из открытых эпизодов; все ID и числа можно найти в `data/dev/`. Суммы в минимальных единицах; у JPY 0 знаков после запятой, у KZT, EUR и USD по 2. Код того же пересчёта лежит в `auditgym/recheck.py`, команда `auditgym datacheck` прогоняет его на любом split.

- **Дубль счёта, `data/dev/ep_02`, I-01.** Счета `D-11328` (INV-4142, выставлен 2026-08-08) и `D-39597` (SF-4142, выставлен 2026-08-06) ссылаются на одну поставку `DN-629429` одного клиента `C-1693` на 1 027,60 USD. Дублем считается выставленный позже, INV-4142. Его проводка `L-40785-1` дебетует 1100 на 93 854 EUR, это и есть сумма ошибки: **93 854**.
- **Курс конвертации, `data/dev/ep_03`, I-02.** Платёж `D-97446` на 379 860 JPY от 2026-12-28. Курс этой даты в `fx.csv` (`FX-2026-12-28-JPY-KZT`) равен 3,13508, значит правильная сумма 379 860 × 3,13508 = 1 190 891,49 KZT, то есть 119 089 149 в минимальных единицах. Проводка `L-53140-1` дебетует банк на 119 940 035. Разница: 119 940 035 − 119 089 149 = **850 886**.
- **Распределение платежа, `data/dev/ep_03`, I-03.** Платёж `D-26002` на 736 660 244 KZT ссылается на счёт INV-5422 (`D-80484`) на ту же сумму, то есть закрывает его полностью. Проводка `L-52969-2` кредитует дебиторку 1100 только на 147 332 049. Не распределено: 736 660 244 − 147 332 049 = **589 328 195**.
- **Отнесение к периоду, `data/dev/ep_03`, I-04.** Счёт `D-60544` (INV-5463) на 1 662 100 JPY: поставка 2027-01-03, то есть в следующем периоде, а проводка `L-53164-1` датирована 2026-12-31, внутри периода. По правилу политики берётся последний курс не позже даты счёта: на 2027-01-03 это курс 2027-01-01 (`FX-2027-01-01-JPY-KZT`), 3,15287. Сумма ошибки равна правильной базовой стоимости проводки: 1 662 100 × 3,15287 = 5 240 385,23 KZT, то есть **524 038 523**.

В связанных сценариях X1 и X2 каждый вывод пересчитывается так же. Его сумма измеряется относительно правильных значений остальных измерений, поэтому одна и та же разница не попадает в два вывода.

## Защиты награды от обмана и как они проверены
- Сопоставление идёт только по полям; текст объяснения не читается. ID сравниваются точно, без нормализации, поэтому гомоглифы и пробелы не проходят.
- Все ID доказательств должны существовать, и среди них должен быть полный допустимый набор.
- Сопоставление взаимно однозначное и детерминированное, повторы считаются FP. Массовые обвинения дают −1, ложное обвинение на чистых книгах тоже даёт −1.
- Строгая схема (msgspec, strict): bool, float и строка вместо целого, лишние поля, превышение лимитов дают ровно −1.
- В eval-режиме награда и диагностика скрыты до конца прогона.
- Проверки: `tests/test_reward.py` (атакующая матрица), `auditgym check` (порядки наград базовых политик).

## Изоляция
- Раннер и дочерняя политика общаются JSON-строками. У дочернего процесса очищенное окружение без соли, пустой cwd, rlimit и тайм-ауты; группа процессов убивается целиком.
- Oracle привилегирован, но действует только через `env.step()`.
- Соль делает перебор сидов бесполезным для политики, импортирующей открытый генератор.
- `leakscan` проверяет траектории; тест подмены эталона проверяет, что наблюдения не зависят от эталона.

## Воспроизводимость
- Потоки ГПСЧ разведены по стадиям и строятся только на `Random.random()`. Деньги в `int`, курсы в `Decimal`, JSON канонический, `tzdata` закреплён.
- Парная проверка: биекция ID плюс перестановка строк. Курсоры — смещения в опубликованном порядке таблицы, поэтому они стабильны в пределах эпизода.
- Oracle отправляет ответ на первом шаге, поэтому его награда (1.0) не зависит от порядка строк.

## Выбор технологий
Ядро написано на Python 3.11 и стандартной библиотеке; кроме неё используются:
- `msgspec` для строгих схем и экспорта JSON Schema;
- `tzdata` для часовых поясов;
- `rich` для таблиц CLI;
- `pytest` и `hypothesis` для тестов;
- `gymnasium` как необязательная обёртка.

От готовых решений отказались так:
- Калькулятор и сопоставление написаны свои. У simpleeval были CVE 2026 года и вычисления во float. У scipy выбор при равенстве зависит от порядка ввода, а это ломает парные проверки.
- CLI построен на argparse и Rich. Node-фреймворки (termcn, Clack) добавили бы второй рантайм на 230 МБ.
